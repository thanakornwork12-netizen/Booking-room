# วิธีเทรน LSTM ในระบบพยากรณ์ความต้องการห้อง (ฉบับอธิบายง่าย)

## 1. เราทำนายอะไร

ทำนาย **"ชั่วโมงการใช้ห้องต่อวัน" ของแต่ละห้อง ล่วงหน้า 14 วัน**

- เทรน **แยกโมเดลต่อห้อง** (ไม่ใช่โมเดลเดียวใช้ทุกห้อง) เพราะแต่ละห้องมีรูปแบบการใช้ต่างกัน
- ปัจจุบันมี 8 ห้องที่มีข้อมูลพอเทรน ห้องละประมาณ 700-800 วัน
- ผลลัพธ์ตัวเลขถูกแปลงเป็นป้ายสี 4 ระดับ (เขียว / เหลือง / ส้ม / แดง) ให้ผู้ใช้ดูหน้าเว็บ
  → ตัวเลข "accuracy" ที่รายงาน คือความแม่นของ **ป้ายสี** ไม่ใช่ความแม่นของตัวเลขดิบ

## 2. ข้อมูลเข้าโมเดล (Input)

ไม่ได้ป้อนแค่ยอดใช้ย้อนหลังอย่างเดียว แต่เป็น **multivariate** — แต่ละวันมีหลายฟีเจอร์
(สร้างใน `build_features()`):

| กลุ่มฟีเจอร์ | ตัวอย่าง | จับอะไร |
|---|---|---|
| ปฏิทิน | วันในสัปดาห์, เดือน, ไตรมาส, สัปดาห์ที่เท่าไรของปี, วันหยุดสุดสัปดาห์ | จันทร์คนใช้เยอะ เสาร์-อาทิตย์ว่าง |
| Lag | ย้อนหลัง 1, 2, 3, 7, 14, 21, 28 วัน | รูปแบบซ้ำรายสัปดาห์ |
| Lag รายปี | ย้อนหลัง 365 วัน + ค่าเฉลี่ย/สูงสุดในหน้าต่าง ~15 วันรอบวันเดียวกันของปีก่อน | ช่วงสอบ / กิจกรรมประจำปีที่วนกลับมา |
| Rolling | ค่าเฉลี่ย/SD/max/min ย้อนหลัง 3, 7, 14, 28 วัน | เทรนด์ระยะสั้น-กลาง |
| ผลต่าง | diff 1 วัน, diff 7 วัน, % เปลี่ยนแปลง 7 วัน | ขาขึ้น/ขาลง |
| Fourier | sin/cos คาบ 7 วัน (3 เทอม) และคาบ 365 วัน (4 เทอม) | ฤดูกาลแบบเรียบ |
| ตารางเทอม | ชั่วโมงที่ถูกจองแบบทั้งเทอมในวันนั้น | ความต้องการที่ล็อกไว้แล้วล่วงหน้า |

**การจัดรูปให้ LSTM:** สไลด์หน้าต่าง `lookback` วัน → 1 ตัวอย่าง
เช่น lookback = 70 คือ "เอาข้อมูล 70 วันล่าสุด ทำนายวันถัดไป"
รูปทรงข้อมูล = `(จำนวนตัวอย่าง, lookback, จำนวนฟีเจอร์+1)`

## 3. สถาปัตยกรรมโมเดล (จริงในโค้ด)

```python
Sequential([
    LSTM(48, return_sequences=False, input_shape=(lookback, n_features)),
    Dropout(0.2),
    Dense(16, activation='relu'),
    Dense(1),
])
optimizer = Adam(learning_rate=0.0005, clipvalue=1.0)
model.compile(optimizer=optimizer, loss='mae', metrics=['mae'])
```

**ทำไมตื้นแค่นี้ (ประเด็นที่ควรคุยกับอาจารย์):**
เคยลอง 3 ชั้น 128→64→32 units แล้ว **overfit และ val curve แกว่งหนัก**
เพราะข้อมูลรายห้องมีแค่ ~700 แถว โมเดลใหญ่จำข้อมูลเทรนได้หมดแต่ทำนายของใหม่ไม่ได้
จึงลดเหลือ LSTM ชั้นเดียว 48 units ซึ่ง converge นิ่งกว่ามาก

- `loss = MAE` เพราะเราสนใจ "พลาดกี่ชั่วโมง" ตรงๆ และ MAE ทนค่า outlier กว่า MSE
- `clipvalue=1.0` กัน exploding gradient
- learning rate ต่ำ (0.0005) เพราะข้อมูลน้อย ก้าวใหญ่แล้วแกว่ง

## 4. การ Scale ข้อมูล (จุดกัน data leakage)

ใช้ `MinMaxScaler` **สองตัวแยกกัน**
- ตัวหนึ่ง scale ฟีเจอร์ input (X)
- อีกตัว scale ค่าที่จะทำนาย (y) — เก็บไว้แปลงผลกลับเป็นหน่วยชั่วโมงตอนทำนาย

**สำคัญ:** `fit()` scaler ด้วย **ข้อมูล train เท่านั้น** ไม่ให้ค่า min/max จาก
validation/test รั่วเข้ามาตอน fit

---

## 5. การแบ่งข้อมูล

แบ่งตามเวลา (ไม่สุ่ม เพราะเป็น time series) เป็น 3 ส่วน:

```
|-------- train 70% --------|-- calibration 15% --|-- test 15% --|
        เทรนโมเดล            หาเกณฑ์ threshold        วัดผลจริง
                              + หาน้ำหนัก ensemble    (ไม่เคยแตะเลย)
```

- **train** — ใช้ปรับ weight ของโมเดล
- **calibration** — ใช้จูนตัวคูณ threshold ที่แบ่งสี และหาน้ำหนักผสม 3 โมเดล
- **test** — ใช้รายงานตัวเลขในเล่มอย่างเดียว ไม่มีอะไรถูกจูนบนส่วนนี้

---

## 6. การเทรน (Training Loop)

| รายการ | ค่าที่ใช้ |
|---|---|
| epochs | ตาม param set (A=10, B=20, C=30, **D=40 ← ค่า production**, E=50) |
| batch size | A=16, B-E=8 |
| lookback | A=20, B=40, C=60, **D=70**, E=90 |
| validation | ใช้ split ที่กันไว้ (ไม่ใช่ `validation_split` แบบสุ่ม) |
| random seed | 42 ทุกที่ (`_seed_everything`) เพื่อให้รันซ้ำได้ผลเดิม |

**EarlyStopping ตั้งแบบพิเศษ** — ตั้ง `patience = จำนวน epoch เต็ม` แปลว่า
**มันไม่มีวันหยุดกลางคัน** เราตั้งใจให้เทรนครบทุก epoch เสมอ เพื่อให้กราฟ
training curve สมบูรณ์เอาไปเทียบ A-E ได้ แต่ยังใช้ประโยชน์ของ
`restore_best_weights=True` คือ **พอจบแล้วดึง weight จาก epoch ที่ val_loss ต่ำสุดกลับมาใช้**
ไม่ใช่ weight ของ epoch สุดท้าย

**ReduceLROnPlateau มีโค้ดอยู่แต่ปิดใช้งาน** (`DISABLE_EARLY_STOPPING = True`)
learning rate จึงคงที่ 0.0005 ตลอด

**Custom callback** (`LSTMClassificationHistoryCallback`) — ทุก epoch จะแปลง
prediction กลับเป็นหน่วยชั่วโมง → แปลงเป็นป้ายสี → คำนวณ accuracy ทั้ง train และ val
บันทึกลง `training_history.jsonl` ทำให้เราพล็อตกราฟ accuracy ต่อ epoch ได้
(ปกติ Keras ให้แค่ loss เพราะนี่เป็นปัญหา regression)

## 7. LSTM ไม่ได้ทำงานคนเดียว — เป็น Ensemble 3 โมเดล

```
LightGBM  ─┐
XGBoost   ─┼─→ ผสมด้วยน้ำหนัก → ค่าทำนายสุดท้าย → แปลงเป็นป้ายสี
LSTM      ─┘
```

น้ำหนักไม่ได้ fix ไว้ แต่ **หาจาก calibration split ของแต่ละห้อง** (adaptive weight)
คือห้องไหนโมเดลไหนแม่นกว่าก็ได้น้ำหนักมากกว่า

**ผลจริงที่ต้องพูดตรงๆ กับอาจารย์:** ใน `consolidated_results.csv` ทุกห้องทุก param set
`lstm_weight_pct = 0.0` — ระบบเลือก LightGBM หรือ XGBoost 100% เสมอ
แปลว่าบนข้อมูลขนาดนี้ (~700 แถวต่อห้อง) **tree-based ชนะ LSTM ชัดเจน**
ตัวนี้เป็นผลการทดลองที่ valid และควรถามอาจารย์ว่าจะวางบทบาทของ LSTM ในเล่มยังไง

---

## 8. สรุปเป็น 6 บรรทัด (ถ้าอาจารย์ถามสั้นๆ)

1. เทรนแยกโมเดลต่อห้อง จากข้อมูลจองจริงย้อนหลังห้องละ ~700-800 วัน
2. ป้อนเข้า LSTM เป็นหน้าต่างเลื่อน 70 วัน แต่ละวันมีหลายสิบฟีเจอร์ (ปฏิทิน + lag + rolling + Fourier + ตารางเทอม)
3. โมเดลตื้นโดยตั้งใจ — LSTM 48 units ชั้นเดียว เพราะข้อมูลน้อย โมเดลลึกกว่านี้ overfit
4. Scale ด้วย MinMaxScaler ที่ fit จาก train เท่านั้น แบ่งข้อมูลตามเวลา 70/15/15
5. เทรนครบทุก epoch แล้วย้อนกลับไปใช้ weight ของ epoch ที่ val_loss ดีที่สุด
6. LSTM ถูกผสมกับ LightGBM/XGBoost แบบ adaptive weight — และผลจริงคือ tree-based ชนะทุกห้อง

---

## 9. คำถามที่อยากได้ความเห็นจากอาจารย์

1. ข้อมูลห้องละ ~700 แถวน้อยเกินไปสำหรับ LSTM หรือไม่ — ควรเก็บ LSTM ไว้เป็น
   contribution หรือเปลี่ยนเรื่องเล่าเป็น "เปรียบเทียบแล้ว tree-based เหมาะกว่า"
2. ควรลองรวมข้อมูลทุกห้องเทรนโมเดลเดียว (global model + room embedding) แทนแยกรายห้องไหม
3. รายงาน accuracy จาก threshold เหมาะสมแค่ไหน — บางห้อง accuracy 0.97 แต่ R² ติดลบ
   (ห้อง 1C-MEETING) เพราะห้องว่างเกือบตลอด ควรเพิ่ม baseline / macro-F1 / confusion matrix ไหม
4. ตอนนี้เทียบ A-E ด้วย seed เดียว (42) ควรรันหลาย seed แล้วรายงาน mean ± std ไหม
5. การปิด ReduceLROnPlateau และบังคับเทรนครบทุก epoch — เป็นการตัดสินใจที่ป้องกันได้หรือควรเปิดกลับ
