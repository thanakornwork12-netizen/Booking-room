1. ภาพรวมโปรเจกต์

สรุปสั้นเว็บจองห้องเรียนและห้องประชุมของ UBU ที่กันจองซ้อน และใช้ AI บอกว่าห้องไหน ช่วงไหน จะถูกใช้เยอะ จองได้ 2 แบบ (รายครั้ง, ทั้งเทอม) ผู้ใช้ 4 บทบาท AI ครอบคลุม 8 ห้อง

ระบบนี้คืออะไร: เว็บแอปจองห้องเรียนและห้องประชุมของมหาวิทยาลัยอุบลราชธานี ที่นอกจากจองได้ยังพยากรณ์ล่วงหน้าว่าห้องไหน ช่วงไหน คนจะใช้เยอะ เพื่อแนะนำผู้ใช้ว่าควรรีบจองหรือยังว่าง

ปัญหาเดิม: ไม่รู้ว่าห้องไหนว่าง, จองซ้อนกันได้, จองผ่านโทรศัพท์หรือแชท ข้อมูลกระจัดกระจาย, ไม่มีข้อมูลบอกว่าห้องไหนใกล้เต็ม, คนจองแล้วไม่มา (no-show)

ทางแก้ที่ระบบทำ:

  1. ระบบจองกลางที่กันจองซ้อนตั้งแต่ระดับฐานข้อมูล (ล็อกแถวห้องตอนจอง)
  2. AI พยากรณ์ความต้องการใช้ห้องล่วงหน้าต่อห้อง แสดงเป็นระดับและสี
  3. ค้นหาและแนะนำห้องตามจำนวนคน อุปกรณ์ อาคาร และช่วงเวลา
  4. ระบบอนุมัติโดยแอดมิน, เช็คอินก่อนใช้ห้อง, ยกเลิกผ่านลิงก์ในอีเมลได้โดยไม่ต้องล็อกอิน
  5. แจ้งเตือนในเว็บทันทีผ่าน WebSocket และแจ้งทางอีเมล

ขอบเขต:

  • จอง 2 แบบ: รายครั้ง (Dynamic Booking) และ ทั้งเทอม (Term Booking ซ้ำทุกสัปดาห์) และมีแบบสลับห้องครึ่งเทอมแรก/ครึ่งหลัง
  • ผู้ใช้ 4 บทบาท: student / lecturer / staff / admin
  • AI ครอบคลุม 8 ห้องที่มีข้อมูลพอ (AI_FORECAST_ROOM_IDS): 2C05-06 (443), 2C09 (445), 2C10-11 (446), 2C16-17 (447), 3C05-06 (448), 1C-MEETING (487), 3C16-17 (505), 4C05 (506) ผู้ใช้ทั่วไปค้นหาและจองได้เฉพาะ 8 ห้องนี้ ส่วนแอดมินเห็นทุกห้องเพื่อจัดการข้อมูล
  • ข้อมูลประวัติการจองจริงจากสำนักคอมพิวเตอร์และเครือข่าย (นำเข้าจาก Excel) ราว 7,250 รายการ

ทำไมเลือกแบบนี้

  • Python ทั้ง backend และ AI: ภาษาเดียวกัน ทำให้ backend เรียกโค้ด AI และเขียนผลลง DB ได้ตรง ไม่ต้องมี service แยก และไลบรารี ML ส่วนใหญ่เป็น Python
  • Django + DRF: มี ORM, migration, admin, ระบบผู้ใช้ในตัว เขียน API ที่มีการตรวจข้อมูลและสิทธิ์ได้เร็ว
  • React SPA แยกจาก backend: แยกหน้าที่ชัดเจน, หน้าเว็บตอบสนองเร็วไม่ต้องโหลดใหม่ทั้งหน้า, API ชุดเดียวกันใช้กับแอปมือถือในอนาคตได้
  • ASGI (daphne) แทน WSGI: WSGI รองรับแค่ request/response ส่วน WebSocket ต้องใช้ ASGI
  • Brevo HTTPS API แทน SMTP: Render บล็อก port 587

ตัวอย่าง: กดจองห้อง 1 ครั้ง เกิดอะไรขึ้นบ้าง

  1. หน้า SearchPage.jsx ส่ง POST /api/bookings/ ผ่าน axios ซึ่งแนบ Authorization: Bearer <access token> ให้อัตโนมัติ
  2. DRF ตรวจ token → รู้ว่าใครจอง (ไม่ใช้ค่าผู้จองที่ส่งมาจากหน้าเว็บ)
  3. BookingCreateSerializer.validate() ตรวจข้อมูล: เวลา, ห้องเปิดใช้งาน, ไม่ย้อนอดีต, จำนวนคน, ไม่ชนการจองอื่น/คาบเรียน/ช่วงปิดซ่อม (เรียกตัวตรวจกลาง booking/overlap.py)
  4. BookingViewSet.perform_create() เปิด transaction → select_for_update() ล็อกแถวห้อง → ตรวจชนซ้ำอีกรอบ (กันสองคนกดพร้อมกัน) → บันทึกสถานะ pending → สร้าง Notification
  5. Signal post_save ทำงานหลัง commit: ส่งอีเมลยืนยันให้ผู้จอง + อีเมลขออนุมัติไปที่ APPROVER_EMAIL + push แจ้งเตือนเข้า WebSocket ให้กระดิ่งเด้ง
  6. หน้าเว็บได้ HTTP 201 แล้วแสดงผล

7. การเข้าสู่ระบบและสิทธิ์

สรุปสั้นล็อกอินลอง LDAP มหาวิทยาลัยก่อน แล้วจึงบัญชีที่สมัครในระบบ ได้ JWT (access 1 วัน, refresh 30 วัน) สมัครเองได้แค่ student/lecturer และ token เก่าใช้ไม่ได้ทันทีเมื่อเปลี่ยนรหัสผ่าน

ล็อกอิน

  • ลำดับ: ลอง LDAP มหาวิทยาลัยก่อน (ldap_auth.py, SIMPLE bind, timeout เชื่อมต่อ 5 วินาที รับข้อมูล 3 วินาที) ถ้าไม่ผ่านจึงตรวจกับบัญชีที่สมัครในระบบ
  • บัญชี LDAP: ล็อกอินครั้งแรกระบบสร้าง User ให้อัตโนมัติ และตั้ง set_unusable_password() คือไม่เก็บรหัสมหาวิทยาลัยไว้เลย ตรวจกับ LDAP ทุกครั้ง
  • เช็คว่าเป็นบัญชี LDAP ด้วย has_usable_password() เท่านั้น เพราะฟิลด์ password ไม่ว่าง (เก็บเป็น !xxxx) เคยเป็นบั๊กจริง
  • สมัครด้วยอีเมล 6611234567@ubu.ac.th ระบบตัดเหลือ 6611234567 ให้ตรงกับชื่อผู้ใช้ LDAP
  • รหัสผ่านผิด: ได้ HTTP 400 "ชื่อผู้ใช้หรือรหัสผ่านไม่ถูกต้อง" ไม่เปิดเผยข้อมูลบัญชี

JWT

  • access token อายุ 1 วัน, refresh token อายุ 30 วัน, เปิด ROTATE_REFRESH_TOKENS (ขอ access ใหม่แล้วได้ refresh ใหม่ด้วย)
  • หน้าเว็บเก็บ token ใน localStorage ถ้าติ๊ก "จดจำการเข้าสู่ระบบ" ไม่ติ๊กเก็บ sessionStorage (หายเมื่อปิดแท็บ)
  • axios มี interceptor: access หมดอายุ (401) จะขอใหม่ด้วย refresh อัตโนมัติ แล้วส่ง request เดิมซ้ำ ถ้า refresh ไม่ผ่านจึงเด้งไปหน้าล็อกอิน

ทับช่วงปิดซ่อมที่ยังไม่ยกเลิกห้องนี้ปิดซ่อมบำรุงอยู่ในช่วงเวลาดังกล่าว
ส่ง status หรือ user มาเองไม่ error แต่ระบบไม่ใช้ค่านั้น (สถานะเป็น pending เสมอ, ผู้จองคือคนที่ล็อกอิน)

การตรวจเกิด 2 ชั้น: ชั้นแรกใน serializer (ตอบเร็ว ข้อความชัด) ชั้นสองใน view ใต้การล็อกแถวห้อง (กันสองคนกดพร้อมกันแล้วผ่านทั้งคู่) ทั้งสองชั้นเรียกฟังก์ชันเดียวกันใน booking/overlap.py

8.3 แก้ไขการจอง

  • PATCH /api/bookings/{id}/ ผ่านกฎชุดเดียวกับตอนสร้าง ส่งมาเฉพาะฟิลด์ที่แก้ได้ ที่เหลือใช้ค่าเดิม และไม่นับตัวเองว่าชนตัวเอง
  • แก้ได้เฉพาะสถานะ pending/approved · แก้แค่ชื่อกิจกรรมของรายการที่เวลาเริ่มผ่านไปแล้วได้ (ตรวจ "ย้อนอดีต" เฉพาะเมื่อเปลี่ยนเวลาเริ่ม)
  • เจ้าของย้ายเวลาหรือห้องของรายการที่อนุมัติแล้ว → กลับไปเป็น pending ต้องอนุมัติใหม่ (บันทึก BookingLog, แจ้งเตือน "แก้ไขการจองแล้ว รออนุมัติใหม่", ส่งอีเมลถึงผู้อนุมัติ) · admin/staff แก้แล้วยังคงอนุมัติอยู่ · เดิมเป็นช่องโหว่: ขออนุมัติช่วงหนึ่งแล้วย้ายไปช่วงอื่นโดยไม่มีใครตรวจ
  • หน้าเว็บไม่มีปุ่มแก้ไข ใช้วิธียกเลิกแล้วจองใหม่

8.4 อนุมัติ / ปฏิเสธ

  • admin/staff เท่านั้น · อนุมัติได้เฉพาะรายการ pending และยังไม่จบเวลา ("อนุมัติได้เฉพาะรายการที่รออนุมัติเท่านั้น")
  • ปฏิเสธใส่เหตุผลได้ (ไม่บังคับ) เหตุผลเก็บใน reject_reason + BookingLog และแสดงในอีเมล/แจ้งเตือน
  • ผลลัพธ์: สร้าง Notification + อีเมลแจ้งผู้จอง
  • คำขอที่หมดเวลา: คำขอที่ยัง pending จนเลยเวลาสิ้นสุดไปแล้ว (จองทั้งเทอม: เลยวันสิ้นสุดเทอม) ถือว่าหมดอายุ ระบบไม่แสดงในรายการของผู้จองและแอดมิน และไม่นับในยอดรออนุมัติ แอดมินจึงไม่ต้องไล่กดปฏิเสธเอง · แถวยังอยู่ในฐานข้อมูลและใน export ไม่ได้ลบจริง

8.5 เช็คอิน

  • เช็คอินได้เฉพาะรายการ approved ตั้งแต่ 15 นาทีก่อนเวลาเริ่ม ถึงเวลาสิ้นสุด (16 นาทีก่อนยังไม่ได้, หลังจบไม่ได้)
  • เช็คอินรายการที่ยังรออนุมัติ: ปฏิเสธและบอกสถานะปัจจุบัน
  • ทำได้ 2 ทาง: ปุ่มในเว็บ (check_in/) หรือลิงก์ในอีเมล (checkin/{token}/ ไม่ต้องล็อกอิน) — ลิงก์เปิดหน้ายืนยันก่อน ต้องกดปุ่มจึงเช็คอิน กันโปรแกรมสแกนลิงก์ในอีเมลเช็คอินแทน
  • ระบบส่งอีเมลเตือนก่อนเวลาเริ่ม 15 นาที พร้อมลิงก์ยกเลิก

8.6 ยกเลิก

  • เจ้าของหรือ admin/staff · ยกเลิกซ้ำได้ "ยกเลิกไปแล้ว" · ผู้ใช้อื่นยกเลิกไม่ได้ "ไม่มีสิทธิ์" · ยกเลิกแล้วช่วงเวลากลับมาว่างทันที
  • ยกเลิกทางอีเมล: เปิดลิงก์ได้หน้ายืนยันก่อน (GET) กดปุ่มจึงยกเลิกจริง (POST) กันโปรแกรมสแกนลิงก์ในอีเมลกดยกเลิกเอง · เช็คอินแล้วยกเลิกทางอีเมลไม่ได้
  • DELETE ถูกปิด การจองไม่ถูกลบจริง เก็บไว้เป็นประวัติ

8.7 จองทั้งเทอม

  • เลือกห้อง, วันในสัปดาห์, เวลา, วันเริ่ม–สิ้นสุดเทอม → สร้างเป็น pending แล้วรอ admin/staff อนุมัติ (เดิมเป็น active ทันทีโดยไม่มีใครตรวจ ทั้งที่กันห้องไว้ทั้งเทอม)
  • วงจรสถานะ: pending → approve → active · pending → reject (ใส่เหตุผลได้) → rejected · pending/active → ยกเลิก → cancelled
  • คำขอที่ pending กันช่วงเวลาไว้แล้ว เหมือน pending ของจองรายครั้ง คนอื่นจองทับไม่ได้ทั้งแบบรายครั้งและทั้งเทอม ถูกปฏิเสธหรือยกเลิกแล้วช่วงเวลาจึงกลับมาว่าง · คาบจะขึ้นปฏิทินและสถานะห้องสดเมื่อ active แล้วเท่านั้น
  • ตอนอนุมัติ ระบบล็อกแถวคาบและแถวห้อง แล้วตรวจการชนซ้ำอีกรอบ · คำขอที่ช่วงเทอมจบไปแล้วอนุมัติไม่ได้ · ทุกการเปลี่ยนสถานะบันทึก BookingLog และแจ้งผู้จองทั้งในเว็บและอีเมล
  • เจ้าของย้ายห้อง/วัน/เวลา/ช่วงเทอมของคาบที่อนุมัติแล้ว → กลับเป็น pending ต้องอนุมัติใหม่ (admin/staff แก้เองไม่ต้อง)
  • ปฏิเสธเมื่อ: วันสิ้นสุดเทอมไม่หลังวันเริ่ม · ช่วงเทอมสิ้นสุดไปแล้ว ("ช่วงเทอมที่เลือกสิ้นสุดไปแล้ว ไม่สามารถจองย้อนหลังได้") ·ช่วงเทอมไม่มีวันนั้นเลย (เลือกเสาร์ แต่เทอมมีแค่ จ.–พ.) · ผู้เข้าร่วมเกินความจุ · ทับคาบทั้งเทอมอื่น · ทับการจองรายครั้งหรือช่วงปิดซ่อมในบางสัปดาห์ (ไล่ตรวจทุกสัปดาห์ ไม่ใช่แค่สัปดาห์แรก)
  • บั๊กที่เคยเจอ: JavaScript นับ 0=อาทิตย์ แต่ Python นับ 0=จันทร์ ต้องแปลงก่อนส่ง (มีคำสั่ง audit_term_dow ไว้ตรวจข้อมูลเก่า)
  • สลับห้อง (split-recommend / split-book): ถ้าไม่มีห้องเดียวว่างทั้งเทอม ระบบหาคู่ห้อง A ครึ่งเทอมแรก + ห้อง B ครึ่งหลัง แล้วส่งคำขอทั้งสองช่วงใน transaction เดียว (ได้ 2 รายการ pending แอดมินอนุมัติทีละรายการ)

8.8 ช่วงปิดซ่อมบำรุง

  • admin/staff สร้างได้ ช่วงเวลาข้ามหลายวันได้
  • ปฏิเสธถ้าทับการจองที่ยังใช้งาน, คาบทั้งเทอม (ไล่ทุกวันในช่วง), หรือช่วงปิดซ่อมอื่น
  • แก้ไขช่วงปิดซ่อม (PATCH/PUT) ผ่านการตรวจชุดเดียวกับตอนสร้าง (เวลาสิ้นสุดต้องหลังเวลาเริ่ม, ไม่ทับ) · ช่วงที่ปิดงานหรือยกเลิกแล้วแก้ไม่ได้ ("แก้ไขไม่ได้ สถานะปัจจุบัน: …")
  • หน้า maintenance/slots/ ใช้ผล AI แนะนำช่วงที่ demand ต่ำให้เลือกปิด แล้วเก็บ predicted_demand_avg ไว้
  • กด complete/cancel แล้วถ้าไม่เหลือช่วงปิดซ่อมค้าง ห้องกลับเป็น available

9. ค้นหาและแนะนำห้อง

สรุปสั้นการค้นหาตัดห้องที่ไม่ว่างในช่วงนั้นออก แนบระดับจาก AI 4 สี แล้วเรียงห้องที่ว่างขึ้นก่อน

  • ค้นหารายครั้ง (rooms/search/): กรองห้องที่จุพอ, ตัดห้องที่ติดการจอง/ปิดซ่อม/คาบเรียนในช่วงนั้นออก, แนบผล AI ของชั่วโมงนั้น แล้วเรียงห้องที่ "ว่างชัวร์" ขึ้นก่อน · ตัดสินจากช่วงเวลาที่ค้นหา ไม่ใช่สถานะห้องตอนนี้: ห้องที่กำลังซ่อมอยู่วันนี้ยังขึ้นในผลค้นหาของวันอื่น ตัดออกถาวรเฉพาะห้องสถานะ disabled
  • ค้นหาทั้งเทอม: ต้องระบุวันในสัปดาห์ ตรวจทุกสัปดาห์ของเทอมด้วยตัวตรวจเดียวกับตอนจอง (find_term_conflict) จึงตัดห้องที่มีการจองรายครั้งในวันนั้นของสัปดาห์ออกด้วย และไม่ตัดห้องที่ปิดซ่อมในวันอื่นของสัปดาห์
  • ตารางห้องรายวัน (availability): แสดงรายการ pending และ checked_in ด้วย เพราะทั้งสองสถานะกันช่วงเวลาอยู่
  • ค้นหาด่วน (suggestions): พิมพ์ตัวเลขล้วน เช่น "40" = จำนวนคน แนะนำห้องที่จุพอเรียงจากพอดีที่สุด ถ้าไม่มีห้องไหนจุพอแนะนำห้องใหญ่สุด · พิมพ์ข้อความ = ค้นชื่อห้อง/อาคาร
  • ห้องใกล้เคียง (dynamic-recommend): เมื่อค้นหาปกติไม่เจอ แนะนำห้องอื่นที่ว่าง ตามลำดับ: เวลาเดิม → เวลาใกล้เคียง ±30/60 นาที (ส่ง suggested_start_time ให้หน้าเว็บเลื่อนเวลาตาม และไม่แนะนำเวลาที่ผ่านไปแล้ว) → ห้องเดิมแต่วันถัดไป 1–3 วัน (suggested_date)
  • แผนสลับห้อง (split-recommend): ตรวจห้องแต่ละครึ่งเทอมด้วย find_term_conflict ตัวเดียวกับตอนจองจริง แผนที่แนะนำจึงกดจองได้ทุกครั้ง
  • ค้นหาใช้กฎเดียวกับการจอง: ค้นเวลาที่ผ่านไปแล้ว จองล่วงหน้าเกิน 365 วัน หรือเทอมที่จบแล้ว ได้ข้อความแจ้งตั้งแต่ตอนค้นหา ไม่ใช่ไปโดนปฏิเสธตอนกดจอง
  • ฟีดหน้าแรก (today-feed): แต่ละห้องโชว์ "ช่วงว่างถัดไปของวันนี้" ห้องที่ใช้อยู่แต่จะว่างบ่ายก็ขึ้นด้วย เพดานคือเวลาปิดอาคาร 21:00
  • สถานะสด (status-feed): ทุกห้องพร้อมสถานะเรียงตามความสำคัญ active > term_active > soon > pending > term_today > booked > free ไม่เปิดเผยชื่อผู้จอง
  • ระดับจาก AI ที่ผู้ใช้เห็น: 🟢 ยังว่าง (likely_available) · 🟡 ควรจอง (recommended) · 🟠 รีบจอง (book_soon) · 🔴 ควรจองตอนนี้เลย (book_now)

10. แจ้งเตือน อีเมล และงานเบื้องหลัง

สรุปสั้นแจ้งเตือนในเว็บเด้งทันทีผ่าน WebSocket อีเมล 10 แบบส่งผ่าน Brevo หลัง commit เท่านั้น งานเบื้องหลังมีงานเดียวคือเตือนเช็คอินก่อน 15 นาที

แจ้งเตือนในเว็บ

  • บันทึก Notification → signal post_save push เข้า group user_{id}_notifications → กระดิ่งในเว็บเด้งทันที ไม่ต้อง refresh
  • ประเภท 10 แบบ: รออนุมัติ, อนุมัติ, ปฏิเสธ, เตือนก่อนใช้, ยกเลิก, จองทั้งเทอมรออนุมัติ, จองทั้งเทอมได้รับอนุมัติ, จองทั้งเทอมถูกปฏิเสธ, แจ้งเตือน demand สูง, ระบบ
  • การจองเปลี่ยนสถานะ → push อัปเดตสถานะห้องเข้า ws/rooms/

อีเมล 10 แบบ (signals.py)

  1. ต้อนรับหลังสมัคร
  2. ลิงก์รีเซ็ตรหัสผ่าน
  3. ขออนุมัติ ส่งถึงผู้อนุมัติ (ทั้งจองรายครั้งและจองทั้งเทอม)
  4. รับคำขอจองแล้ว (รออนุมัติ)
  5. ยืนยันการจองที่อนุมัติแล้ว (มีลิงก์เช็คอิน/ยกเลิก)
  6. รับคำขอจองทั้งเทอมแล้ว (รออนุมัติ)
  7. ยืนยันจองทั้งเทอมที่อนุมัติแล้ว
  8. แจ้งปฏิเสธจองทั้งเทอม พร้อมเหตุผล
  9. แจ้งยกเลิก
  10. แจ้งปฏิเสธ พร้อมเหตุผล
  • ส่งหลัง transaction commit แล้วเท่านั้น (send_email_after_commit) กันส่งอีเมลของรายการที่ rollback ไป
  • ผ่าน Brevo HTTPS API (room_booking/email_backend.py)
  • ข้อความที่ผู้ใช้พิมพ์ (ชื่อกิจกรรม, ชื่อวิชา, ชื่อผู้จอง, ชื่อห้อง) ถูก escape ก่อนใส่ลงอีเมล HTML · เวลาในอีเมลแสดงเป็นเวลาไทย
  • thread ที่ส่งอีเมลเบื้องหลังปิด connection ฐานข้อมูลของตัวเองเมื่อจบ (เดิมค้างไว้ 1 connection ต่ออีเมล)

งานเบื้องหลัง (scheduler.py)

  • มีงานเดียว: ทุก 1 นาที หาการจอง approved ที่จะเริ่มในอีก 14–16 นาที ยังไม่เช็คอินและยังไม่เคยเตือน → ส่งอีเมลเตือนพร้อมลิงก์ยกเลิก แล้วตั้ง reminded=True กันส่งซ้ำ
  • การเทรน AI ไม่ได้อยู่ใน scheduler ต้องรันคำสั่งเอง (หัวข้อ 12)

12. AI ที่ใช้งานจริง (production: ml/saved/forecast.py)

สรุปสั้นตัวที่ใช้จริงคือ forecast.py: โมเดลรายห้องแบบ recursive แต่ละห้องใช้ LightGBM หรือ XGBoost ตัวเดียว เพราะโมเดลเดี่ยวชนะการถ่วงน้ำหนักทั้ง 56 กรณี และชนะ seasonal naive 6 จาก 8 ห้อง

ต้องแยกให้ออก: production ยังรัน forecast.py (โมเดลรายห้องแบบ recursive) ส่วน งานวิจัยล่าสุด คือ direct forecaster (หัวข้อ 13) ถ้ากรรมการถามว่า "ตัวไหนใช้จริง" ต้องตอบให้ตรง
  • โจทย์: พยากรณ์ชั่วโมงการใช้ห้องต่อวัน (time series regression) แล้วตัดเป็นระดับ (classification)
    • ตอนประเมิน: 3 คลาส low / medium / urgent
    • ในแอป: 4 ระดับ low/medium/high/urgent และ availability 4 ค่า (หัวข้อ 9)
  • ข้อมูล: ประวัติการจองจาก Excel ของสำนักคอมฯ แตก booking ออกเป็นรายวัน (expand_bookings_to_daily, cap 12 ชม./วัน) และรวมช่วงเวลาแบบ interval-union เพื่อให้ booking ซ้ำไม่ถูกนับสองเท่า
  • Features: lag, rolling mean/std, calendar (dow, month, sin/cos ที่ผูกกับปฏิทินจริง), วันหยุดไทย, peer rooms
  • โมเดล: LightGBM + XGBoost ต่อห้อง (เดิมมี LSTM เป็น ensemble 3 ตัว แต่ LSTM ได้น้ำหนัก 0% แทบทุกห้อง ตอนนี้เหลือ LGB+XGB)
    • หาน้ำหนักถ่วงสองโมเดล (Weighted Averaging) จาก calibration slice
    • จากนั้น _prefer_best_single_if_beats_blend() ตรวจว่าโมเดลเดี่ยวชนะ blend ไหม ถ้าชนะใช้ตัวเดียว
    • ผลจริง: ใน consolidated_results.csv ทั้ง 56 แถว (8 ห้อง × 7 ชุด) น้ำหนักเป็น 100/0 ทุกแถว คือโมเดลเดี่ยวชนะทุกกรณี (LightGBM 47, XGBoost 9)
  • Split: ตัดที่ "วันตัดร่วม" เดียวกันทุกห้องและตัดที่ขอบวัน (split_dataset_from_excel.py) แล้วแบ่ง train เป็น train/calibration ส่วน test ไม่เคยใช้ตัดสินใจอะไร
    • ก่อนแก้มี 2 รอยรั่ว: (1) เคยแบ่ง 80% แยกรายห้อง ทำให้ช่วงเวลาข้ามห้องคาบเกี่ยวกัน (2) เคยตัดตามจำนวนแถว ทำให้วันเดียวกันอยู่ทั้ง train และ test
  • Leak ที่เคยแก้ (a019b76): feature diff_1, diff_7, pct_chg_7 คำนวณจาก y ของวันเดียวกัน (lag_1 + diff_1 = y) ทำให้ R² ≈ 1.00 หลอก ตัดออกแล้ว
  • Cold start (ห้องใหม่หรือข้อมูลน้อย): ยืมข้อมูลห้อง room_type เดียวกัน
    • Tier (get_data_tier): full ≥200 การจองและ ≥60 วัน · medium ≥60 และ ≥21 วัน · sparse ≥14 และ ≥7 วัน · ต่ำกว่านั้น cold_start
    • Seasonal median prior (build_cold_start_prior): มัธยฐานชั่วโมงรายวันของห้องประเภทเดียวกัน (ไม่รวมห้องตัวเอง) ตาม (วันในสัปดาห์, เดือน) ถ้าไม่มีใช้ตามวันในสัปดาห์ ถ้ายังไม่มีใช้มัธยฐานรวม ใช้มัธยฐานเพราะทนค่าผิดปกติ
    • Peer profile (fit_peer_profile): feature เสริมของทุกห้อง ไม่ใช่เฉพาะ cold start ตัดข้อมูลห้องอื่นที่ cutoff_date กัน leak
    • 8 ห้องที่ใช้ AI ตอนนี้น่าจะอยู่ tier full ทั้งหมด (ยังไม่ได้รันเช็ก) เส้นทาง cold start มีไว้สำหรับห้องใหม่
    • ตอบกรรมการ: "ห้องใหม่ยังไม่มีประวัติ จึงยืมรูปแบบของห้องประเภทเดียวกันมาทายก่อน พอข้อมูลสะสมถึงเกณฑ์ก็เปลี่ยนไปใช้โมเดลเต็ม"
  • รันจริง: รันด้วยคำสั่ง python ml/saved/forecast.py --retrain --param-set D (ค่าเริ่มต้นของ --param-set คือ D) แล้วเขียนตาราง DemandForecast ให้หน้าเว็บอ่าน · ไม่ได้ตั้งเวลาให้รันเองใน scheduler.py · คำสั่งอื่น: --import-excel (นำเข้าข้อมูลจริง), --show-metrics

13. AI งานวิจัยล่าสุด: Direct multi-horizon forecaster

สรุปสั้นงานวิจัยล่าสุดทายแต่ละวันล่วงหน้า (1–14 วัน) ตรง ๆ ด้วยโมเดลเดียวรวม 8 ห้อง เพื่อแก้ปัญหา error สะสมของแบบ recursive ยังไม่ได้ใช้บน production

ไฟล์: direct_forecast.py, train_direct.py, train_direct_sets.py, test_direct.py

ทำไมเปลี่ยนจาก recursive → direct (คำถามยอดฮิต)

  • ปัญหาของ recursive: เทรนแบบทาย 1 วันล่วงหน้า แล้วเอาไปป้อนซ้ำ 14 รอบ
    • ตอนเทรน lag_1 เป็นค่าจริง แต่ตอนใช้งานเป็นค่าที่โมเดลทายเอง error จึงสะสม (train/serve mismatch)
    • วัดแล้วเสียไปประมาณ 4 จุด accuracy
  • Direct: แต่ละแถวคือ (origin t, horizon h) แล้วทาย y[t+h] ตรง ๆ จากข้อมูลที่รู้ ณ t เท่านั้น
    • h=14 จึงซื่อตรงเท่ากับ h=1 และการเทรนตรงกับการใช้งานจริง
    • HORIZON = 14 วัน

การออกแบบ

  • Pooled model ตัวเดียวรวม 8 ห้อง: ห้องขยับไปพร้อมกัน (weekly corr 0.68–0.93) เพราะปฏิทินการศึกษาเดียวกัน จึงได้ข้อมูลประมาณ 8 เท่า ใส่ room_ix กับ room_scale เป็น feature
  • Features ~50 ตัว: lag0/1/2/6/13/20/27 · rolling mean/std/max (7/14/28/56) · peer rooms · calendar ของวันเป้าหมาย (dow, month, sin/cos, holiday) · ประวัติวันเดียวกันของสัปดาห์ (sdow4/8/12, prev_dow1-4) · year_ago · multi-day block (blk_*) · categorical: dow, room_ix, month
  • ตัด feature ที่ตรวจแล้วไม่มีประโยชน์: term_* 18 คอลัมน์เป็นศูนย์ทั้งหมด (ไม่มี term schedule ของ 8 ห้องนี้) · created_at เป็นเวลา bulk-import (7,251 แถวเวลาเดียวกัน) จึงไม่มี lead-time signal
  • Quantile regression 10 ตัว (q = 0.05…0.95) ได้การกระจายของค่าพยากรณ์ ไม่ใช่แค่ค่าเดียว
  • Output 2 ค่า (สองคำถาม สอง loss):
    • argmax_class: เลือกระดับที่มี probability mass มากสุด ใช้กับระดับ/สี (median บนข้อมูลเบ้ขวาจะทาย urgent เป็น low/medium ไปครึ่งหนึ่ง)
    • median_forecast: ค่ากลาง ทำให้ MAE ต่ำสุด ใช้แสดงชั่วโมง
  • Block floor: booking ยาวหลายวันที่เริ่มแล้วถือเป็นข้อเท็จจริง ค่าพยากรณ์ห้ามต่ำกว่าชั่วโมงที่ถูกจองไว้แล้ว (1.9% ของ booking แต่คิดเป็น 16–61% ของชั่วโมง)
  • Engine: LightGBM กับ XGBoost แข่งกันบน calibration แล้วแต่ละห้องใช้ engine ที่ชนะ
  • Strategy รายห้อง: argmax_class / median / dow_profile / constant ต้องชนะ default เกิน 2×SE = 2·√(0.25/n) ถึงจะเปลี่ยน (เคยเปลี่ยนด้วย margin 0.002 แล้ว test ตก 8 จุด: fleet 0.800 → 0.764)
  • ไม่มี early stopping: เทรนครบ rounds แล้วอ่าน checkpoint ย้อนหลัง เลือก round ที่ accuracy ดีสุดและ round ที่ MAE ดีสุดแยกกัน ตัดสินบน calibration เท่านั้น · calibration = 12.5% ของช่วง train, MIN_HISTORY = 400 วัน
  • Test: ORIGIN_STEP = 1 ทุกวันเป็น origin ประมาณ 3,100 แถวต่อห้อง (live job รันทุก 14 วัน)

แอดมินยกเลิกการจองของคนอื่นเงียบๆเจ้าของจองทั้งเทอมไม่รู้ตัวเลย (รายครั้งได้แค่อีเมล)แจ้งเตือนในเว็บ + อีเมลยกเลิกจองทั้งเทอม
ยกเลิกหลังเช็คอิน เว็บกับอีเมลผลไม่ตรงกันAPI ยกเลิกได้ ลิงก์อีเมลยกเลิกไม่ได้ยกเลิกได้เฉพาะก่อนเช็คอินทุกช่องทาง

17. ให้ตรงกับเล่มวิทยานิพนธ์

สรุปสั้นจุดที่เล่มอาจไม่ตรงกับระบบจริง: ชนิดฐานข้อมูล, ผลของ Weighted Averaging, คำว่า "อย่างมีนัยสำคัญ" และ LSTM

จุดที่เล่มกับระบบจริงอาจไม่ตรงกัน ต้องตอบให้สอดคล้อง
  • ฐานข้อมูล: บทคัดย่อเขียน SQLite · ระบบรองรับทั้งสองแบบ ค่าเริ่มต้นเป็น SQLite และสลับเป็น PostgreSQL เมื่อตั้ง env DATABASE_URL ซึ่ง production (Neon) และเครื่องที่พัฒนาอยู่ตอนนี้ใช้ PostgreSQL ถ้าเล่มจะคง SQLite ไว้ ควรเพิ่มว่า production ใช้ PostgreSQL
  • Weighted Averaging: ระบบคำนวณการถ่วงน้ำหนักจริง แต่ผลคือโมเดลเดี่ยวชนะ blend ทุกกรณี (น้ำหนัก 100/0 ครบ 56 แถว) อย่าเขียนหรือพูดว่า "Weighted Averaging ลดความคลาดเคลื่อนได้อย่างมีนัยสำคัญเมื่อเทียบกับแบบจำลองเดี่ยว" ให้พูดว่า "เปรียบเทียบการถ่วงน้ำหนักกับโมเดลเดี่ยว แล้วระบบเลือกแบบที่ดีที่สุดรายห้อง ผลคือโมเดลเดี่ยวดีกว่าในข้อมูลชุดนี้"
  • "อย่างมีนัยสำคัญ": ยังไม่มีการทดสอบนัยสำคัญทางสถิติ อย่าใช้คำนี้กับผลของงานเราเอง
  • บทที่ 1: ปิดย่อหน้าเป็นคำถามวิจัย "Weighted Averaging ให้ผลดีกว่าโมเดลเดี่ยวหรือไม่" ผลที่ออกมาจึงเป็นคำตอบ ไม่ขัดกับบทนำ
  • LSTM: ถ้าเล่มยังพูดถึง LSTM ให้ระบุว่าลองแล้วได้น้ำหนัก 0% จึงตัดออก

18. ข้อจำกัดและจุดที่ยังไม่สมบูรณ์

สรุปสั้นพูดข้อจำกัดเองก่อนโดนถาม: ข้อมูลมีแค่ 8 ห้อง ประมาณ 3 ปี, production ยังเป็น recursive, ยังไม่มีสถิติทดสอบนัยสำคัญ, WebSocket ใช้ได้ในโปรเซสเดียว

ด้านข้อมูลและ AI (พูดเองก่อนโดนถาม)

  • มีแค่ 8 ห้องที่ข้อมูลพอ และข้อมูลประมาณ 3 ปี มีรอบปีการศึกษาน้อย
  • ไม่มีตารางเรียนจริง (term schedule ว่าง) และไม่มี lead time (created_at เป็นเวลา import)
  • Class imbalance: ห้องว่างเยอะ ทำให้ accuracy ดูดีเกินจริง จึงรายงาน balanced accuracy และ F1 ด้วย
  • มี booking ซ้ำแบบ exact 67 แถวที่ไม่ได้ลบ (interval-union ช่วยไม่ให้นับซ้ำ)
  • Production ยังใช้ recursive ส่วน direct ยังเป็นงานทดลอง
  • เทียบกับ baseline ยังไม่มีสถิติทดสอบนัยสำคัญ
  • 2C09 ระดับการใช้ลดลงครึ่งหนึ่งระหว่าง train กับ test (distribution shift)
  • calibration มีหน้าต่างเดียวและตรงกับช่วงปิดเทอม จึงยากกว่า test และแยก set A–D ไม่ออก (ดูคำถามในหัวข้อ 20)

ด้านระบบ (พบจากการอ่านโค้ด ยังไม่ได้แก้)

  • WebSocket ใช้ InMemoryChannelLayer: ใช้ได้ในโปรเซสเดียว ถ้าขยายหลายโปรเซสต้องเปลี่ยนเป็น Redis · ช่อง ws/retrain/ ยังไม่มีโค้ดส่วนไหนส่งความคืบหน้าเข้าไป
  • เวลาปิดอาคาร 21:00 ใช้แค่แสดงผล ไม่ได้บังคับตอนจอง (เพดานความยาวมีแล้ว 21 วัน)
  • ช่วงปิดซ่อมที่สร้างไว้ล่วงหน้า พอถึงเวลาเริ่มซ่อม ฟิลด์ room.status ไม่เปลี่ยนเป็น "ซ่อมบำรุง" เอง (ไม่มีงานตั้งเวลา) แต่สถานะสดและการกันจองดูจากช่วงเวลาจริงแล้ว
  • JWT เก็บใน localStorage/sessionStorage และ access token อายุ 1 วัน ถ้าเกิด XSS token จะหลุดได้นานกว่าแบบอายุสั้น

ตัวระบบ

ระบบเขียนด้วยภาษาอะไรบ้าง?
  • Backend และ AI เป็น Python (Django + Django REST Framework, LightGBM, XGBoost)
  • Frontend เป็น JavaScript ด้วย React 19 + Vite จัดสไตล์ด้วย Tailwind CSS
  • ฐานข้อมูลเข้าถึงผ่าน Django ORM ไม่ได้เขียน SQL ตรง ใช้ PostgreSQL ทั้งในเครื่องที่พัฒนาและบน production (Neon) ถ้าไม่ตั้ง DATABASE_URL จะใช้ SQLite
ทำไมเลือก Django ไม่ใช้ Node.js / Laravel?
  • AI เขียนด้วย Python อยู่แล้ว ใช้ภาษาเดียวกันทำให้ backend เรียกโค้ด AI และเขียนผลพยากรณ์ลงฐานข้อมูลได้ตรง ไม่ต้องมี service แยกสื่อสารข้ามภาษา
  • Django มี ORM, migration, admin, ระบบผู้ใช้ในตัว DRF ทำให้เขียน API ที่ตรวจข้อมูลและสิทธิ์ได้เร็ว
ทำไมแยก frontend กับ backend?

แยกหน้าที่ชัด, หน้าเว็บตอบสนองเร็ว (SPA), API ชุดเดียวใช้กับแอปมือถือได้ในอนาคต, พัฒนาและ deploy แยกกันได้

ระบบกันจองซ้อนยังไง?
  • ตรวจ 3 แหล่ง: การจองรายครั้งที่ยังใช้งาน (pending/approved/checked_in), คาบเรียนทั้งเทอม, ช่วงปิดซ่อม
  • เงื่อนไขทับคือ เริ่มใหม่ < จบเดิม และ จบใหม่ > เริ่มเดิม ชนขอบพอดีไม่นับ
  • ตรวจสองชั้น: serializer (ตอบเร็ว) และใน view ใต้ select_for_update (กันกดพร้อมกัน)
จองพร้อมกัน 2 คนเกิดอะไร?

select_for_update ล็อกแถว Room ใน transaction คนที่สองต้องรอจนคนแรก commit แล้วตรวจซ้ำจะเห็นว่าห้องไม่ว่าง ได้ข้อความ "มีคนจองพร้อมกัน"

จองทั้งเทอมต้องอนุมัติไหม ต่างจากจองรายครั้งยังไง?
  • ต้องอนุมัติเหมือนกัน: สร้างแล้วเป็น pending ให้ admin/staff กด approve จึงเป็น active หรือ reject พร้อมเหตุผล
  • เหตุผล: จองทั้งเทอมกันห้องไว้ทุกสัปดาห์ตลอดเทอม ผลกระทบมากกว่าจองรายครั้ง จึงไม่ควรมีผลโดยไม่มีคนตรวจ
  • ระหว่างรออนุมัติ ช่วงเวลาถูกกันไว้แล้ว กันสองคำขอที่ทับกันเข้าไปรออนุมัติพร้อมกัน
  • ที่ต่าง: จองทั้งเทอมไม่มีขั้นเช็คอิน และสถานะที่ใช้งานอยู่เรียกว่า active (จองรายครั้งเรียก approved)
ทำไมต้องมีเช็คอิน?

แก้ปัญหา no-show: เปิดเช็คอินก่อน 15 นาทีถึงเวลาจบ พร้อมอีเมลเตือนที่มีลิงก์ยกเลิก ถ้าไม่มาก็ยกเลิกได้ง่าย ห้องกลับมาว่างให้คนอื่น

ยกเลิกทางอีเมลไม่ต้องล็อกอิน ไม่อันตรายเหรอ?
  • ลิงก์มี UUID สุ่มเฉพาะการจองนั้น เดาไม่ได้ และใช้ได้กับการจองนั้นเท่านั้น
  • เปิดลิงก์แล้วเห็นหน้ายืนยันก่อน ต้องกดปุ่มอีกครั้ง กันโปรแกรมสแกนลิงก์ในอีเมลยกเลิกเอง
ทำไม WebSocket ไม่ใช้ polling?

push ทันที ไม่ต้องยิง request ซ้ำ ๆ จึงประหยัด server ต้องใช้ ASGI/Channels

ความปลอดภัยรหัสผ่าน LDAP?

ไม่เก็บรหัส (unusable password) ตรวจกับ LDAP ทุกครั้งที่ล็อกอิน

JWT เก็บ localStorage ไม่เสี่ยง XSS เหรอ?
  • เสี่ยงถ้ามี XSS จึงลดความเสี่ยงด้วยการที่ React escape ข้อความอัตโนมัติ และ escape หน้าที่ Python สร้างเอง
  • access token ตั้งไว้ 1 วัน ถ้าจะปลอดภัยขึ้นควรลดอายุและย้ายไป httpOnly cookie (future work)
ทดสอบระบบยังไง เจออะไรบ้าง?
  • เขียนเทสต์อัตโนมัติ 328 เคสยิง API จริงบนฐานข้อมูลทดสอบแยก ครอบคลุมแผน T01–T30 เคสขอบของการจอง ความปลอดภัย สิทธิ์แอดมิน และอีเมล ผ่านทั้งหมด
  • จากการทดสอบเจอและแก้บั๊ก 70 รายการ เช่น แก้ไขการจองแล้วข้ามการตรวจ, ย้ายเวลาหลังอนุมัติโดยไม่ต้องอนุมัติใหม่, จองสลับห้องทับการจองอื่น, ห้องที่เช็คอินอยู่ขึ้นว่าว่าง, เวลาในอีเมลเตือนเร็วไป 7 ชั่วโมง, XSS ในหน้าจากลิงก์อีเมล (หัวข้อ 16)
ทำไมรหัสผ่านผิดได้ 400 ไม่ใช่ 401?

view ล็อกอิน (LDAPTokenObtainPairView) ตอบ 400 เมื่อข้อมูลล็อกอินไม่ผ่าน ผลตรงตามที่ต้องการคือเข้าระบบไม่ได้ ไม่ได้ token และไม่เปิดเผยข้อมูลบัญชี

AI

Weighted Averaging ใช้จริงไหม ทำไมผลเป็นโมเดลเดี่ยว?
  • ระบบคำนวณน้ำหนักถ่วงจริงบน calibration แล้วเทียบกับโมเดลเดี่ยว
  • ในข้อมูลชุดนี้โมเดลเดี่ยวดีกว่าทุกกรณี (56/56) ระบบจึงเลือกโมเดลเดี่ยวรายห้อง LightGBM 47 กรณี XGBoost 9 กรณี
  • เหตุผลที่เป็นไปได้: LightGBM และ XGBoost เป็น gradient boosting บน feature ชุดเดียวกัน ความผิดพลาดจึงไปทางเดียวกัน การเฉลี่ยจึงไม่ค่อยช่วย
ทำไมไม่ใช้ deep learning / LSTM?
  • ลองแล้ว (อยู่ใน ensemble เดิม) แต่ได้น้ำหนัก 0% แทบทุกห้อง
  • ข้อมูลรายวันต่อห้องมีแค่หลักร้อยถึงพันแถว ซึ่งน้อยเกินสำหรับ LSTM
  • Gradient boosting บนข้อมูลตาราง + lag features ทำได้ดีกว่า เทรนเร็วกว่า และอธิบายได้ (feature importance)
ทำไมใช้ LightGBM และ XGBoost ทั้งคู่?
  • คนละแบบการโตของต้นไม้ (LGB โต leaf-wise, XGB โต level-wise) เหมาะกับห้องต่างกัน
  • ให้แข่งกันบน calibration แล้วเลือกรายห้อง ผลคือ direct set C ใช้ LGB 6 ห้อง XGB 2 ห้อง
รู้ได้ไงว่าไม่ overfit?
  • test ไม่เคยถูกใช้ตัดสินใจ ทุกอย่างเลือกบน calibration
  • set D (capacity สูงสุด) มี train 0.94 แต่ test ตกเหลือ 0.802 ขณะที่ C ได้ 0.813 จึงเห็นจุดที่ overfit เริ่ม
Data leakage ป้องกันยังไง?
  • ตัดด้วยวันร่วมที่ขอบวัน และ feature ใช้เฉพาะข้อมูล ณ origin
  • เคยเจอ leak diff_1 (R² ≈ 1) แล้วแก้ใน a019b76
  • sin/cos ผูกกับวันในปฏิทินจริง ไม่ใช่ index ของแถว (c5983a7)
Accuracy 81% ดีจริงไหม เทียบอะไร?
  • เทียบกับ seasonal naive 73.7% และ naive 62.1%
  • MAE ลดจาก 2.07 เหลือ 1.44 ชม.
  • ยอมรับข้อจำกัดเรื่องโปรโตคอลที่ไม่เท่ากันและไม่มี CI (ดูหัวข้อ 14)
ทำไม accuracy ไม่พอ ต้องมี balanced accuracy?
  • class imbalance: ถ้าทาย "low" ตลอดก็ได้ accuracy สูงในห้องที่ว่าง (เช่น 1C-MEETING)
  • balanced accuracy เฉลี่ย recall ของแต่ละคลาส จึงไม่โดนหลอกแบบนั้น
Calibration กับ validation ต่างกันไหม?
  • ความหมายทั่วไป: validation ใช้เลือก hyperparameter/rounds/โมเดล · calibration ใช้ปรับค่าที่ทายให้ตรงความจริง (Platt, isotonic) · test ใช้วัดผลครั้งสุดท้ายเท่านั้น
  • ในงานนี้ calibration slice ทำทั้งสองอย่าง: แบบ validation (เลือก LGB/XGB ต่อห้อง, หาน้ำหนัก ensemble, เลือก round จาก checkpoint, เลือก strategy) และแบบ calibration (fit_prediction_calibration เรียนการแปลงค่าพยากรณ์ให้ตรงค่าจริง)
  • แบ่งตามเวลา [train | calibration (ท้าย train) | test] ไม่สุ่ม เพราะเป็น time series
  • ตอบกรรมการ: "calibration ในงานนี้ก็คือ validation set ครับ ใช้เลือกโมเดลและ hyperparameter และใช้ปรับเทียบค่าพยากรณ์ด้วย เลยตั้งชื่อว่า calibration ส่วน test แยกไว้วัดผลอย่างเดียว"
  • ระวัง: probability calibration (ทาย 70% แล้วเกิดจริงประมาณ 70%, ดูด้วย reliability diagram) งานนี้ยังไม่ได้วัด

Quantile regression คืออะไร ทำไมใช้?
  • ทาย percentile ต่าง ๆ ด้วย pinball loss จึงได้การกระจายของค่า
  • เอาไปคำนวณ probability ของแต่ละระดับได้ แล้วเลือกระดับที่น่าจะเป็นที่สุด ซึ่งตรงกับ metric ที่ใช้วัด
Recursive vs direct ต่างกันยังไง?

ดูหัวข้อ 13: recursive ป้อนค่าที่ตัวเองทายกลับเข้าไปจน error สะสม ส่วน direct ทายแต่ละ horizon ตรง ๆ ทำให้ train กับ serve ตรงกัน

ทำไม pooled model ไม่แยกห้อง?
  • ห้องขยับตามปฏิทินเดียวกัน (corr 0.68–0.93) รวมกันแล้วได้ข้อมูลประมาณ 8 เท่า
  • ความต่างของแต่ละห้องจับด้วย room_ix, room_scale และ strategy รายห้อง
ทำไม early stopping ไม่ใช้?
  • early stopping ดู pinball loss ของ quantile ทีละตัว ซึ่งเป็นแค่ตัวแทนของสิ่งที่เราสนใจ
  • เราจึงเทรนครบแล้วประเมิน ensemble ทั้งชุดที่ checkpoint ด้วย metric จริง (accuracy, MAE) แล้วเลือก round
ทำไมต้องมี margin 2×SE ตอนเลือก strategy?
  • calibration มีประมาณ 109 วัน จึงมี SE ราว 0.048 ชนะกันไม่กี่ทศนิยมถือเป็น noise
  • เคยทำให้ test ตก 8 จุดมาแล้ว
AI ช่วยผู้ใช้/แอดมินจริงยังไง?
  • ผู้ใช้เห็นสี "ควรรีบจอง" และห้องที่ว่างถูกเรียงขึ้นก่อน
