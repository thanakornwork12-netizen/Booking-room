1. ภาพรวม

ปัญหา: ไม่รู้ว่าห้องไหนว่าง, จองซ้อนได้, ไม่มีข้อมูลบอกว่าห้องไหนใกล้เต็ม, คนจองแล้วไม่มา (no-show)

ทางแก้:

  1. ระบบจองกลางแบบ real-time ที่กันจองซ้อนระดับฐานข้อมูล
  2. AI พยากรณ์ demand ล่วงหน้าต่อห้อง แสดงเป็นสี/ระดับ
  3. แนะนำห้องตามจำนวนคน อุปกรณ์ อาคาร และเวลา
  4. ยกเลิกผ่านลิงก์ในอีเมลได้โดยไม่ต้องล็อกอิน
  5. แจ้งเตือนผ่าน WebSocket

ขอบเขต:

  • จอง 2 แบบ: รายครั้ง (Dynamic) และทั้งเทอม (Term, ซ้ำทุกสัปดาห์)
  • 4 role: student / lecturer / staff / admin
  • AI ครอบคลุม 8 ห้องที่มีข้อมูลพอ (AI_FORECAST_ROOM_IDS): 2C05-06(443), 2C09(445), 2C10-11(446), 2C16-17(447), 3C05-06(448), 1C-MEETING(487), 3C16-17(505), 4C05(506)

4. Authentication / Security

  • Login: ลอง LDAP ก่อน ถ้าไม่ผ่าน fallback ไปบัญชี local
    • login ผ่าน LDAP แล้วสร้าง/อัปเดต User ให้อัตโนมัติ และเรียก set_unusable_password() (ไม่เก็บรหัสมหาวิทยาลัย)
    • เช็คว่าเป็นบัญชี LDAP ด้วย has_usable_password() เท่านั้น เพราะค่า password ไม่ว่าง (เป็น !xxxx) เคยเป็นบั๊กจริง
  • JWT: access (อายุสั้น) + refresh (อายุยาว) เก็บ localStorage หรือ sessionStorage ตาม "จำฉันไว้"
  • สิทธิ์:
    • staff/admin เท่านั้นที่เข้า Admin Dashboard ได้
    • สมัครเองเลือก role admin ไม่ได้ (เคยเป็นช่องโหว่: ยิง API พร้อม role=admin แล้วผ่าน แก้แล้ว)
    • เมื่ออนุมัติ ระบบแจ้ง approver ทางอีเมลและให้ role admin แก่บัญชีนั้น (commit fc54c6e)
  • Reset password: ใช้ PasswordResetTokenGenerator (token หมดอายุเมื่อรหัสเปลี่ยน ไม่ต้องมีตาราง token) บัญชี LDAP ให้ติดต่อสำนักคอมฯ แทน
  • Race condition: ใช้ transaction.atomic() + select_for_update() ล็อกแถว Room ตอนจอง และล็อกแถว Booking ตอน approve/reject
  • ลิงก์อีเมล: ใช้ UUID สุ่ม (checkin_token) เดาไม่ได้
  • รู้ไว้: ข้อมูลมี booking title ที่เป็น XSS (stored) ในห้อง 2C05-06 จึงต้อง escape ตอนแสดงผล (React escape ให้อัตโนมัติ ยกเว้นใช้ dangerouslySetInnerHTML)

5. Flow การจอง

  1. ค้นหา/แนะนำ
    • กรองห้องที่ capacity พอ และไม่ทับกับ 3 แหล่ง (Booking, MaintenanceBlock, TermBooking)
    • แนบผล AI แล้วเรียงห้องที่ "ว่างชัวร์" ขึ้นก่อน
    • quick search: พิมพ์ตัวเลขล้วนจะถือเป็นจำนวนคน
  2. จองรายครั้ง: backend ตรวจซ้อนอีกรอบ แล้วสร้างสถานะ pending และส่งอีเมลพร้อมลิงก์ยกเลิก
    • การเช็ค conflict นับ pending, approved และ checked_in ด้วย (ถ้าไม่นับ pending อาจอนุมัติทับกันได้)
  3. อนุมัติ: admin/staff กด approve หรือ reject (ต้องใส่เหตุผล) แล้วระบบส่งอีเมลผ่าน signal และบันทึก BookingLog
    • อนุมัติคำขอที่เลยเวลาไปแล้วไม่ได้ แต่ reject ได้
  4. จองทั้งเทอม
    • เลือกวันคาบแรกกับวันสิ้นเทอม ระบบดึงวันในสัปดาห์ให้เอง
    • ตรวจ conflict ทุกสัปดาห์ ไม่ใช่แค่สัปดาห์แรก
    • ถ้าไม่มีห้องเดียวที่ว่างทั้งเทอม มี split_recommend/split_book (ใช้ห้อง A ครึ่งแรก ห้อง B ครึ่งหลัง)
    • บั๊กที่เคยเจอ: JS นับ 0=อาทิตย์ แต่ Python นับ 0=จันทร์ จึงต้องแปลงก่อนส่ง
  5. ยกเลิกผ่านอีเมล: ใช้ token ไม่ต้องล็อกอิน มาแทนกฎ "เช็คอินภายใน 15 นาที" เดิม
  6. แจ้งเตือน: Notification ถูก post_save แล้วส่งเข้า group user_{id}_notifications ให้กระดิ่งใน frontend เด้งทันที

6. AI เวอร์ชันที่ใช้งานจริง (production: ml/saved/forecast.py)

ต้องแยกให้ออก: production ยังรัน forecast.py (โมเดลรายห้องแบบ recursive) ส่วน งานวิจัยล่าสุด คือ direct forecaster (หัวข้อ 7) ถ้ากรรมการถามว่า "ตัวไหนใช้จริง" ต้องตอบให้ตรง
  • โจทย์: พยากรณ์ชั่วโมงการใช้ห้องต่อวัน (time series regression) แล้วตัดเป็นระดับ (classification)
    • ตอนประเมิน: 3 คลาส low / medium / urgent
    • ในแอป: 4 ระดับ low/medium/high/urgent และ availability 4 ค่า likely_available / recommended / book_soon / book_now
  • ข้อมูล: ประวัติการจองจาก Excel ของสำนักคอมฯ แตก booking ออกเป็นรายวัน (expand_bookings_to_daily, cap 12 ชม./วัน) และรวมช่วงเวลาแบบ interval-union เพื่อให้ booking ซ้ำไม่ถูกนับสองเท่า
  • Features: lag, rolling mean/std, calendar (dow, month, sin/cos ที่ผูกกับปฏิทินจริง), วันหยุดไทย, peer rooms
  • โมเดล: LightGBM + XGBoost ต่อห้อง (เดิมมี LSTM เป็น ensemble 3 ตัว แต่ LSTM ได้น้ำหนัก 0% แทบทุกห้อง ตอนนี้จึงเหลือ LGB+XGB)
    • น้ำหนัก ensemble หาจาก calibration slice
    • ถ้าโมเดลเดี่ยวชนะ blend ก็ใช้ตัวเดียว (เลยเห็น winner 100% บ่อย)
  • Split: ตัดที่ "วันตัดร่วม" เดียวกันทุกห้องและตัดที่ขอบวัน (split_dataset_from_excel.py) แล้วแบ่ง train เป็น train/calibration ส่วน test ไม่เคยใช้ตัดสินใจอะไร
    • ก่อนแก้มี 2 รอยรั่ว: (1) เคยแบ่ง 80% แยกรายห้อง ทำให้ช่วงเวลาข้ามห้องคาบเกี่ยวกัน (2) เคยตัดตามจำนวนแถว ทำให้วันเดียวกันอยู่ทั้ง train และ test
  • Leak ที่เคยแก้ (a019b76): feature diff_1, diff_7, pct_chg_7 คำนวณจาก y ของวันเดียวกัน (lag_1 + diff_1 = y) ทำให้ R² ≈ 1.00 หลอก ตัดออกแล้ว
  • Cold start (ห้องใหม่หรือข้อมูลน้อยจนโมเดลเรียนจากห้องตัวเองไม่ได้): ยืมข้อมูลห้อง room_type เดียวกัน
    • Tier (get_data_tier):
      • full: ≥200 การจอง และ ≥60 วัน
      • medium: ≥60 การจอง และ ≥21 วัน
      • sparse: ≥14 การจอง และ ≥7 วัน
      • ต่ำกว่านั้นเป็น cold_start
    • Seasonal median prior (build_cold_start_prior): ตัวทายสำรองของห้อง cold start
      • เฉลี่ยชั่วโมงรายวันของห้องประเภทเดียวกัน (ไม่รวมห้องตัวเอง)
      • หามัธยฐานตาม (วันในสัปดาห์, เดือน) ถ้าไม่มีใช้มัธยฐานของวันในสัปดาห์ ถ้ายังไม่มีใช้มัธยฐานรวม
      • ใช้มัธยฐานเพราะทนค่าผิดปกติ ข้อมูลน้อยแต่ยังเสถียร
    • Peer profile (fit_peer_profile): feature เสริมของทุกห้อง ไม่ได้ใช้เฉพาะ cold start
      • มัธยฐานของห้องประเภทเดียวกันตาม (วัน, เดือน) และ (วัน, อยู่ในเทอมหรือไม่)
      • ตัดข้อมูลห้องอื่นที่ cutoff_date เพื่อกัน leak
    • 8 ห้องที่ใช้ AI ตอนนี้น่าจะอยู่ tier full ทั้งหมด (ยังไม่ได้รันเช็ก) ถ้าใช่ เส้นทาง cold start มีไว้สำหรับห้องใหม่ในอนาคต
    • ตอบกรรมการ: "ห้องใหม่ยังไม่มีประวัติ จึงยืมรูปแบบของห้องประเภทเดียวกันมาทายก่อน พอข้อมูลสะสมถึงเกณฑ์ก็เปลี่ยนไปใช้โมเดลเต็ม"
  • รันจริง: booking/scheduler.py เรียก forecast.py --retrain แล้วเขียนตาราง DemandForecast ให้ UI อ่าน

7. AI งานวิจัยล่าสุด: Direct multi-horizon forecaster

ไฟล์: direct_forecast.py, train_direct.py, train_direct_sets.py, test_direct.py

ทำไมเปลี่ยนจาก recursive → direct (คำถามยอดฮิต)

  • ปัญหาของ recursive: เทรนแบบทาย 1 วันล่วงหน้า แล้วเอาไปป้อนซ้ำ 14 รอบ
    • ตอนเทรน lag_1 เป็นค่าจริง แต่ตอนใช้งานเป็นค่าที่โมเดลทายเอง error จึงสะสม (train/serve mismatch)
    • วัดแล้วเสียไปประมาณ 4 จุด accuracy
  • Direct: แต่ละแถวคือ (origin t, horizon h) แล้วทาย y[t+h] ตรง ๆ จากข้อมูลที่รู้ ณ t เท่านั้น
    • h=14 จึงซื่อตรงเท่ากับ h=1 และการเทรนตรงกับการใช้งานจริง
    • HORIZON = 14 วัน

การออกแบบ

  • Pooled model ตัวเดียวรวม 8 ห้อง:
    • ห้องขยับไปพร้อมกัน (weekly corr 0.68–0.93) เพราะปฏิทินการศึกษาเดียวกัน จึงได้ข้อมูลประมาณ 8 เท่า
    • ใส่ room_ix กับ room_scale เป็น feature
  • Features ~50 ตัว:
    • lag0/1/2/6/13/20/27
    • rolling mean/std/max (7/14/28/56)
    • peer rooms
    • calendar ของวันเป้าหมาย (dow, month, sin/cos, holiday)
    • ประวัติวันเดียวกันของสัปดาห์ (sdow4/8/12, prev_dow1-4)
    • year_ago
    • multi-day block (blk_*)
    • categorical: dow, room_ix, month
  • ตัด feature ที่ตรวจแล้วไม่มีประโยชน์:
    • term_* 18 คอลัมน์เป็นศูนย์ทั้งหมด (ไม่มี term schedule ของ 8 ห้องนี้)
    • created_at เป็นเวลา bulk-import (7,251 แถวเวลาเดียวกัน) จึงไม่มี lead-time signal
  • Quantile regression 10 ตัว (q = 0.05…0.95) ได้การกระจายของค่าพยากรณ์ ไม่ใช่แค่ค่าเดียว
  • Output 2 ค่า (สองคำถาม สอง loss):
    • argmax_class: เลือกระดับที่มี probability mass มากสุด ใช้กับระดับ/สี (median บนข้อมูลเบ้ขวาจะทาย urgent เป็น low/medium ไปครึ่งหนึ่ง)
    • median_forecast: ค่ากลาง ทำให้ MAE ต่ำสุด ใช้แสดงชั่วโมง
  • Block floor: booking ยาวหลายวันที่เริ่มแล้วถือเป็นข้อเท็จจริง ค่าพยากรณ์ห้ามต่ำกว่าชั่วโมงที่ถูกจองไว้แล้ว (1.9% ของ booking แต่คิดเป็น 16–61% ของชั่วโมง)
  • Engine: LightGBM กับ XGBoost แข่งกันบน calibration แล้วแต่ละห้องใช้ engine ที่ชนะ
  • Strategy รายห้อง: argmax_class / median / dow_profile / constant
    • ต้องชนะ default เกิน 2×SE = 2·√(0.25/n) ถึงจะเปลี่ยน
    • เคยเปลี่ยนด้วย margin 0.002 แล้ว test ตก 8 จุด (fleet 0.800 → 0.764)
  • ไม่มี early stopping: เทรนครบ rounds แล้วอ่าน checkpoint ย้อนหลัง
    • เลือก round ที่ accuracy ดีสุด และ round ที่ MAE ดีสุดแยกกัน โดยตัดสินบน calibration เท่านั้น
    • calibration = 12.5% ของช่วง train, MIN_HISTORY = 400 วัน
  • Test: ORIGIN_STEP = 1 ทุกวันเป็น origin ประมาณ 3,100 แถวต่อห้อง (live job รันทุก 14 วัน)

9. Deploy

  • Render.com (render.yaml) รัน daphne (ASGI) และใช้ whitenoise เสิร์ฟ static
  • DB: Neon Postgres (ใช้ dj-database-url), secrets อยู่ใน env (python-dotenv)
  • อีเมลผ่าน Brevo API และ CORS ให้ frontend คนละ origin เรียกได้
  • โมเดลและ meta (saved_models*, saved_meta*) อยู่ใน .gitignore ไม่ถูก commit

10. ข้อจำกัด (พูดเองก่อนโดนถาม)

  • มีแค่ 8 ห้องที่ข้อมูลพอ และข้อมูลประมาณ 3 ปี มีรอบปีการศึกษาน้อย
  • ไม่มีตารางเรียนจริง (term schedule ว่าง) และไม่มี lead time (created_at เป็นเวลา import)
  • Class imbalance: ห้องว่างเยอะ ทำให้ accuracy ดูดีเกินจริง จึงรายงาน balanced accuracy และ F1 ด้วย
  • มี booking ซ้ำแบบ exact 67 แถวที่ไม่ได้ลบ (interval-union ช่วยไม่ให้นับซ้ำ)
  • Production ยังใช้ recursive ส่วน direct ยังเป็นงานทดลอง
  • เทียบกับ baseline ยังไม่มีสถิติทดสอบนัยสำคัญ
  • 2C09 ระดับการใช้ลดลงครึ่งหนึ่งระหว่าง train กับ test (distribution shift)
  • calibration มีหน้าต่างเดียวและตรงกับช่วงปิดเทอม จึงยากกว่า test และแยก set A–D ไม่ออก (ดูคำถามในหัวข้อ 12)

11. Future work

  • ประเมินบนวันเดียวกัน + bootstrap CI + Diebold-Mariano test

  • Retrain อัตโนมัติพร้อม monitoring drift และแอปมือถือ (ใช้ API เดิม)

12. คำถามที่น่าจะโดน + แนวตอบ

ทำไมไม่ใช้ deep learning / LSTM?
  • ลองแล้ว (อยู่ใน ensemble เดิม) แต่ได้น้ำหนัก 0% แทบทุกห้อง
  • ข้อมูลรายวันต่อห้องมีแค่หลักร้อยถึงพันแถว ซึ่งน้อยเกินสำหรับ LSTM
  • Gradient boosting บนข้อมูลตาราง + lag features ทำได้ดีกว่า เทรนเร็วกว่า และอธิบายได้ (feature importance)
ทำไมใช้ LightGBM และ XGBoost ทั้งคู่?
  • คนละแบบการโตของต้นไม้ (LGB โต leaf-wise, XGB โต level-wise) เหมาะกับห้องต่างกัน
  • ให้แข่งกันบน calibration แล้วเลือกรายห้อง ผลคือ C ใช้ LGB 6 ห้อง XGB 2 ห้อง
รู้ได้ไงว่าไม่ overfit?
  • test ไม่เคยถูกใช้ตัดสินใจ ทุกอย่างเลือกบน calibration
  • set D (capacity สูงสุด) มี train 0.94 แต่ test ตกเหลือ 0.802 ขณะที่ C ได้ 0.813 จึงเห็นจุดที่ overfit เริ่ม
Data leakage ป้องกันยังไง?
  • ตัดด้วยวันร่วมที่ขอบวัน และ feature ใช้เฉพาะข้อมูล ณ origin
  • เคยเจอ leak diff_1 (R² ≈ 1) แล้วแก้ใน a019b76
  • sin/cos ผูกกับวันในปฏิทินจริง ไม่ใช่ index ของแถว (c5983a7)
Accuracy 81% ดีจริงไหม เทียบอะไร?
  • เทียบกับ seasonal naive 73.7% และ naive 62.1%
  • MAE ลดจาก 2.07 เหลือ 1.44 ชม.
  • ยอมรับข้อจำกัดเรื่องโปรโตคอลที่ไม่เท่ากันและไม่มี CI (ดูหัวข้อ 8)
ทำไม accuracy ไม่พอ ต้องมี balanced accuracy?
  • class imbalance: ถ้าทาย "low" ตลอดก็ได้ accuracy สูงในห้องที่ว่าง (เช่น 1C-MEETING)
  • balanced accuracy เฉลี่ย recall ของแต่ละคลาส จึงไม่โดนหลอกแบบนั้น
Calibration กับ validation ต่างกันไหม?
  • ความหมายทั่วไป:
    • validation ใช้เลือก hyperparameter/rounds/โมเดล
    • calibration ใช้ปรับค่าที่ทายให้ตรงความจริง (Platt, isotonic)
    • test ใช้วัดผลครั้งสุดท้ายเท่านั้น
  • ในงานนี้ calibration slice ทำทั้งสองอย่าง:
    • แบบ validation: เลือก LGB/XGB ต่อห้อง, หาน้ำหนัก ensemble, เลือก round จาก checkpoint, เลือก strategy
    • แบบ calibration: fit_prediction_calibration เรียนการแปลงค่าพยากรณ์ให้ตรงค่าจริง
  • แบ่งตามเวลา [train | calibration (ท้าย train) | test] ไม่สุ่ม เพราะเป็น time series
  • ตอบกรรมการ: "calibration ในงานนี้ก็คือ validation set ครับ ใช้เลือกโมเดลและ hyperparameter และใช้ปรับเทียบค่าพยากรณ์ด้วย เลยตั้งชื่อว่า calibration ส่วน test แยกไว้วัดผลอย่างเดียว"
  • ระวัง: probability calibration (ทาย 70% แล้วเกิดจริงประมาณ 70%, ดูด้วย reliability diagram) งานนี้ยังไม่ได้วัด

Quantile regression คืออะไร ทำไมใช้?
  • ทาย percentile ต่าง ๆ ด้วย pinball loss จึงได้การกระจายของค่า
  • เอาไปคำนวณ probability ของแต่ละระดับได้ แล้วเลือกระดับที่น่าจะเป็นที่สุด ซึ่งตรงกับ metric ที่ใช้วัด
Recursive vs direct ต่างกันยังไง?

ดูหัวข้อ 7: recursive ป้อนค่าที่ตัวเองทายกลับเข้าไปจน error สะสม ส่วน direct ทายแต่ละ horizon ตรง ๆ ทำให้ train กับ serve ตรงกัน

ทำไม pooled model ไม่แยกห้อง?
  • ห้องขยับตามปฏิทินเดียวกัน (corr 0.68–0.93) รวมกันแล้วได้ข้อมูลประมาณ 8 เท่า
  • ความต่างของแต่ละห้องจับด้วย room_ix, room_scale และ strategy รายห้อง
จองพร้อมกัน 2 คนเกิดอะไร?

select_for_update ล็อกแถว Room ใน transaction ทำให้คนที่สองต้องรอ แล้วจะเห็นว่าห้องไม่ว่าง

ทำไม WebSocket ไม่ใช้ polling?

push ทันที ไม่ต้องยิง request ซ้ำ ๆ จึงประหยัด server ต้องใช้ ASGI/Channels

ความปลอดภัยรหัสผ่าน LDAP?

ไม่เก็บรหัส (unusable password) ตรวจกับ LDAP ทุกครั้งที่ login

JWT เก็บ localStorage ไม่เสี่ยง XSS เหรอ?
  • เสี่ยงถ้ามี XSS จึงลดความเสี่ยงด้วย access token อายุสั้นและ React escape output อัตโนมัติ
  • ทางที่ดีกว่าคือ httpOnly cookie (ใส่เป็น future work)
ทำไม early stopping ไม่ใช้?
  • early stopping ดู pinball loss ของ quantile ทีละตัว ซึ่งเป็นแค่ตัวแทนของสิ่งที่เราสนใจ
  • เราจึงเทรนครบแล้วประเมิน ensemble ทั้งชุดที่ checkpoint ด้วย metric จริง (accuracy, MAE) แล้วเลือก round
ทำไมต้องมี margin 2×SE ตอนเลือก strategy?
  • calibration มีประมาณ 109 วัน จึงมี SE ราว 0.048 ชนะกันไม่กี่ทศนิยมถือเป็น noise
  • เคยทำให้ test ตก 8 จุดมาแล้ว
AI ช่วยผู้ใช้/แอดมินจริงยังไง?
  • ผู้ใช้เห็นสี "ควรรีบจอง" และห้องที่ว่างถูกเรียงขึ้นก่อน
  • แอดมินเลือกช่วงปิดซ่อมตอนที่ demand ต่ำ (MaintenanceBlock.predicted_demand_avg)
