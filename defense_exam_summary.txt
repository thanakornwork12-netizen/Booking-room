เอกสารสรุปเตรียมสอบป้องกันโปรเจกต์
ระบบจองห้องเรียน/ประชุมอัจฉริยะ (UBU Smart Room Booking)
สำนักคอมพิวเตอร์และเครือข่าย มหาวิทยาลัยอุบลราชธานี
================================================================================
เอกสารนี้อธิบายทุกส่วนของระบบตั้งแต่ภาพรวมจนถึงรายละเอียดทางเทคนิค เรียงลำดับ
จากภาพกว้างไปแคบ อ่านจากบนลงล่างได้ต่อเนื่อง (บทที่ 1-8) ตามด้วยชุดคำถาม-
แนวทางตอบแบบละเอียดแบ่งหมวด (บทที่ 9), ข้อจำกัดของงานที่ควรพูดถึงเอง (บทที่
10), แนวทางพัฒนาต่อ (บทที่ 11), เทคนิคการตอบคำถามในห้องสอบ (บทที่ 12) และ
อภิธานศัพท์เผื่อถูกขอให้อธิบายคำศัพท์สด (ภาคผนวก ก) — ทุกตัวเลข/สถาปัตยกรรม
ที่อ้างถึงเช็คตรงกับโค้ดจริงในระบบ ไม่ได้เดา


================================================================================
บทที่ 1: ภาพรวมโปรเจกต์ (Project Overview)
================================================================================

1.1 ปัญหาที่ระบบแก้ไข (Problem Statement)
--------------------------------------------
ห้องเรียน/ห้องประชุมของหน่วยงานมีจำนวนจำกัด แต่ความต้องการใช้งานไม่แน่นอน
(ขึ้นกับตารางเรียน ช่วงสอบ กิจกรรมพิเศษ) การจองแบบเดิม (จองผ่านเจ้าหน้าที่/
กระดาษ/ไม่มีระบบกลาง) มีปัญหา:
  - ไม่รู้ว่าห้องไหนว่างจริง ณ เวลานั้น ต้องถามเจ้าหน้าที่/เดินไปดูเอง
  - จองซ้อนกันได้ (สอง event จองห้องเดียวกันเวลาเดียวกัน)
  - ไม่มีข้อมูลช่วยตัดสินใจว่าห้องไหน "น่าจะเต็ม" ต้องรีบจอง หรือห้องไหนว่าง
    แน่นอนไม่ต้องรีบ
  - ผู้จองที่ไม่มาใช้งานจริง (no-show) ทำให้ห้องถูกกันไว้เปล่าๆ โดยไม่มีกลไก
    ยกเลิกที่สะดวก

1.2 แนวทางแก้ปัญหาของระบบนี้
--------------------------------------------
  1) ระบบจองกลางแบบ real-time ผ่านเว็บ พร้อมกันชนการจองซ้อน (conflict
     prevention ระดับฐานข้อมูล)
  2) โมเดล AI พยากรณ์ "ความต้องการใช้ห้อง" ล่วงหน้าเป็นรายชั่วโมง/รายวัน
     ต่อห้อง จากข้อมูลการจองย้อนหลัง → แสดงเป็นสถานะสีเขียว/เหลือง/ส้ม/แดง
     ให้ผู้ใช้ตัดสินใจได้เร็วขึ้นว่าห้องนี้ "ควรรีบจอง" หรือ "ยังไม่ต้องรีบ"
  3) ระบบแนะนำห้อง (recommend) ที่เข้าใจเงื่อนไขผู้ใช้ (จำนวนคน, อุปกรณ์,
     อาคาร, เวลา) แล้วจัดอันดับห้องที่เหมาะสมให้อัตโนมัติ
  4) ยกเลิกการจองได้ทันทีผ่านลิงก์ในอีเมล ไม่ต้องล็อกอินเข้าระบบ ลดปัญหา
     ห้องถูกกันไว้เปล่าๆ
  5) แจ้งเตือนแบบ real-time (WebSocket) เมื่อสถานะการจองเปลี่ยน

1.3 ขอบเขตของระบบ (Scope)
--------------------------------------------
  - จองห้องได้ 2 รูปแบบ: จองรายวัน/รายครั้ง (Dynamic Booking) และจองทั้งเทอม
    แบบล็อกวันซ้ำทุกสัปดาห์ (Term Booking เช่น จองห้องเรียนทุกวันพุธ 13:00-15:00
    ตลอดเทอม)
  - รองรับ 4 บทบาทผู้ใช้: นักศึกษา, อาจารย์, เจ้าหน้าที่, ผู้ดูแลระบบ (admin)
  - AI พยากรณ์ครอบคลุมเฉพาะห้องที่มีข้อมูลย้อนหลังจริงเพียงพอ ปัจจุบันมี 8 ห้อง
    (ระบุ ID ตายตัวใน backend: AI_FORECAST_ROOM_IDS)
  - Deploy ใช้งานจริงบน Render (เว็บ) + Neon (ฐานข้อมูล Postgres) + Brevo
    (ส่งอีเมล)


================================================================================
บทที่ 2: สถาปัตยกรรมระบบโดยรวม (System Architecture)
================================================================================

2.1 แนวคิดสถาปัตยกรรม
--------------------------------------------
เป็นสถาปัตยกรรมแบบ Client-Server แยก Backend/Frontend ชัดเจน คุยกันผ่าน
REST API (HTTP) สำหรับข้อมูลทั่วไป และ WebSocket สำหรับข้อมูล real-time
(แจ้งเตือน, สถานะห้องเปลี่ยน)

    [ React (Vite) — Frontend ]
              |  HTTPS (REST API, JSON)
              |  WebSocket (แจ้งเตือน real-time)
              v
    [ Django + Django REST Framework — Backend ]
              |
              +-- Django Channels (ASGI, รัน daphne) — จัดการ WebSocket
              +-- APScheduler — งาน cron เบื้องหลัง (เตือนก่อนใช้ห้อง 15 นาที)
              +-- ml/ (โมดูลพยากรณ์ AI แยกจาก business logic หลัก)
              |
              v
    [ PostgreSQL (Neon, บน production) ]

    บริการภายนอก:
      - Brevo REST API → ส่งอีเมล (ยืนยันการจอง, ลิงก์ยกเลิก, รีเซ็ตรหัสผ่าน)
      - LDAP มหาวิทยาลัย → ยืนยันตัวตนบัญชีจริงของนักศึกษา/บุคลากร

2.2 เหตุผลที่เลือกใช้ Django Channels (ไม่ใช่ Django ธรรมดา)
--------------------------------------------
Django แบบมาตรฐาน (WSGI) รองรับได้แค่ HTTP request-response ธรรมดา ไม่รองรับ
WebSocket ระบบนี้ต้องการแจ้งเตือนแบบ real-time (เช่น แอดมินอนุมัติการจองแล้ว
ผู้ใช้เห็นแจ้งเตือนทันทีโดยไม่ต้อง refresh หน้า) จึงต้องใช้ Django Channels
(ASGI) รันด้วย daphne แทน runserver ปกติ — endpoint WebSocket คือ
/ws/notifications/

2.3 ทำไมแยก Backend/Frontend เป็นคนละโปรเจกต์ (ไม่ใช้ Django Template)
--------------------------------------------
  - แยก concern ชัดเจน: Backend โฟกัสที่ business logic + data + AI, Frontend
    โฟกัสที่ UX
  - React SPA (Single Page Application) ให้ประสบการณ์ลื่นกว่า ไม่ reload
    หน้าทั้งหมดทุกครั้งที่กดปุ่ม
  - Backend เป็น REST API ล้วนๆ ทำให้ในอนาคตต่อกับแอปมือถือได้โดยไม่ต้อง
    แก้ backend เลย

2.4 เทคโนโลยีที่ใช้ทั้งหมด (Tech Stack)
--------------------------------------------
Backend:
  - Python 3 + Django + Django REST Framework (REST API)
  - Django Channels + daphne (ASGI server, WebSocket)
  - djangorestframework-simplejwt (JWT authentication)
  - django-apscheduler (cron job เบื้องหลัง เก็บ log ใน DB)
  - django-cors-headers (อนุญาต frontend คนละ origin เรียก API ได้)
  - django-import-export (export ข้อมูลเป็น Excel ใน admin)
  - whitenoise (serve static files บน production)
  - PostgreSQL (production: Neon; local dev: PostgreSQL/SQLite ก็ได้)

Frontend:
  - React 19 + Vite (build tool, dev server เร็ว)
  - React Router v6 (routing แบบ SPA)
  - Tailwind CSS v4 (utility-first CSS)
  - axios (เรียก REST API)
  - lucide-react (ไอคอน)

โมดูล AI/ML (แยกอยู่ใน ml/saved/):
  - TensorFlow/Keras (LSTM)
  - LightGBM, XGBoost (gradient boosting)
  - scikit-learn (metrics, scaler, train/test split logic)
  - pandas, numpy (data processing)

Infrastructure (production):
  - Render.com — host เว็บเซอร์วิส (รัน daphne)
  - Neon — PostgreSQL แบบ serverless (ฐานข้อมูลจริง)
  - Brevo — ส่งอีเมลผ่าน REST API แทน SMTP (Render บล็อก outbound port 587
    จึงส่งอีเมลผ่าน HTTPS API แทน)


================================================================================
บทที่ 3: โครงสร้างฐานข้อมูล (Database Schema)
================================================================================

ตารางหลักทั้งหมด (Django Model) และความสัมพันธ์:

1) User (ขยายจาก Django AbstractUser)
   - role: admin / staff / lecturer / student
   - faculty, phone, student_id (unique), avatar

2) Building — อาคาร (name, code, description)

3) Room — ห้อง
   - FK -> Building
   - name, floor, capacity, room_type
   - status: available / occupied / maintenance / disabled
   - unique_together (building, name) — ห้องชื่อเดียวกันซ้ำในอาคารเดียวกันไม่ได้

4) Facility / RoomFacility — อุปกรณ์ประจำห้อง (ตาราง master + ตารางเชื่อม
   many-to-many แบบมี quantity เช่น "โปรเจกเตอร์ x1")

5) Booking — การจองรายวัน/รายครั้ง
   - FK -> User, Room
   - title, attendees, start_time, end_time
   - status: pending / approved / rejected / cancelled / completed / checked_in
   - checked_in, checked_in_at, checkin_token (UUID สุ่ม ใช้เป็นกุญแจลิงก์
     เช็คอิน/ยกเลิกผ่านอีเมลโดยไม่ต้องล็อกอิน)
   - approved_by

6) TermBooking — การจองทั้งเทอม (ล็อกวันซ้ำรายสัปดาห์)
   - FK -> User, Room
   - subject_name, subject_code, attendees
   - day_of_week (0=จันทร์ ... 6=อาทิตย์), start_time, end_time (เป็น TimeField
     ไม่ใช่ DateTimeField เพราะซ้ำทุกสัปดาห์)
   - term_start, term_end, term_name
   - status: active / cancelled / ended
   - มี method get_weekly_slots() คำนวณวันที่จริงทั้งหมดในเทอมที่ตรงกับ
     day_of_week ที่เลือก (ใช้เช็ค conflict และคำนวณจำนวนสัปดาห์)

7) MaintenanceBlock — ช่วงเวลาที่ห้องถูกล็อกไว้ซ่อมบำรุงเชิงป้องกัน (กันการ
   จองทับ) มี predicted_demand_avg เก็บค่าพยากรณ์เฉลี่ยช่วงที่เลือกปิดซ่อม
   (ให้แอดมินเลือกปิดซ่อมช่วงที่ AI บอกว่า demand ต่ำที่สุด)

8) DemandForecast — ผลพยากรณ์ AI ต่อห้อง ต่อวัน ต่อชั่วโมง
   - unique_together (room, forecast_date, hour) — 1 ห้อง 1 วัน 1 ชั่วโมง
     มีค่าพยากรณ์ได้ค่าเดียว
   - predicted_demand (0.0-1.0), demand_level (low/medium/high/urgent),
     availability (likely_available/recommended/book_soon/book_now),
     confidence, term_demand, dynamic_demand (แยกว่า demand มาจากฝั่งจองเทอม
     หรือจองรายวันเท่าไหร่)

9) Notification — แจ้งเตือนผู้ใช้ (ผูกกับ Booking/TermBooking ได้), ส่งผ่าน
   WebSocket ทันทีที่ถูกสร้าง (Django signal ดัก post_save)

10) BookingLog — ประวัติการเปลี่ยนสถานะการจอง (audit trail)

11) RoomUsageStat — สถิติการใช้งานห้องรายวัน (จำนวนจอง, utilization rate)
    สำหรับ dashboard รายงาน

ความสัมพันธ์หลัก: User 1-N Booking, User 1-N TermBooking, Room 1-N Booking,
Room 1-N TermBooking, Room 1-N DemandForecast, Room 1-N MaintenanceBlock

บทที่ 4: ระบบยืนยันตัวตน (Authentication)
================================================================================

4.1 กลไกการ Login
--------------------------------------------
ระบบรองรับ 2 ทาง โดยลอง LDAP ก่อนเสมอ แล้ว fallback ไปรหัสผ่าน local:

  1) LDAP มหาวิทยาลัย (ทางหลัก) — ผู้ใช้กรอกรหัสนักศึกษา/username จริงของ
     มหาวิทยาลัย ระบบ bind เข้า LDAP server เพื่อตรวจรหัสผ่าน ถ้าถูกต้อง
     จะสร้างหรืออัปเดต Django User ให้อัตโนมัติ (ไม่ต้องสมัครสมาชิกล่วงหน้า)
     รองรับกรอกได้ทั้งรูปแบบ "6612345678", "6612345678@ubu.ac.th" หรืออีเมล
     จริงของมหาวิทยาลัยที่ไม่ตรงกับเลขนักศึกษาโดยตรง

  2) บัญชี Local (fallback) — สำหรับผู้ที่สมัครสมาชิกเองผ่านระบบ (ไม่ใช่
     บัญชีมหาวิทยาลัย) เมื่อ LDAP bind ไม่ผ่าน ระบบจะลองตรวจรหัสผ่านแบบ
     Django ปกติ (hashed password ในฐานข้อมูล) ต่อ

  จุดสำคัญ: บัญชีที่ล็อกอินผ่าน LDAP จะถูกเรียก `set_unusable_password()`
  (ไม่เก็บรหัสผ่านมหาวิทยาลัยไว้เอง) เพราะรหัสผ่านจริงตรวจกับ LDAP server
  โดยตรงทุกครั้ง ไม่ได้ cache ไว้ในฐานข้อมูลตัวเอง — ปลอดภัยกว่า

  จุดที่มักเข้าใจผิด (และเคยเป็นบั๊กจริงในระบบนี้มาก่อน — ดูหัวข้อ 9.3):
  `set_unusable_password()` ของ Django ไม่ได้ทำให้ `user.password` เป็น
  ค่าว่างเปล่า แต่เก็บเป็นสตริงรูปแบบ `!<สุ่มอักขระ>` (ไม่ใช่ hash ที่ใช้
  งานได้จริง แต่ก็ไม่ใช่ค่าว่าง) ดังนั้นการเช็คว่า "เป็นบัญชี LDAP หรือไม่"
  ต้องเช็คด้วย `user.has_usable_password()` (คืน False สำหรับบัญชี LDAP)
  เท่านั้น จะเช็คแบบ `not user.password` ตรงๆ ไม่ได้ เพราะสตริงที่ไม่ว่าง
  จะถูกตีความว่าเป็น truthy เสมอ ไม่ว่าจะ "ใช้งานได้จริง" หรือไม่ก็ตาม

4.2 JWT (JSON Web Token)
--------------------------------------------
เมื่อยืนยันตัวตนผ่านแล้ว ระบบออก JWT สองส่วน: access token (อายุสั้น ใช้แนบ
ทุก request) และ refresh token (อายุยาวกว่า ใช้ขอ access token ใหม่โดยไม่
ต้อง login ซ้ำ) เก็บไว้ที่ browser (localStorage หรือ sessionStorage ขึ้นกับ
ผู้ใช้ติ๊ก "จำฉันไว้" หรือไม่)

4.3 ระบบสิทธิ์ (Authorization / Role-based access)
--------------------------------------------
4 role: student, lecturer, staff, admin — staff/admin เท่านั้นที่เข้าหน้า
Admin Dashboard ได้ (อนุมัติ/ปฏิเสธการจอง, จัดการห้อง, ดูรายงาน) การสมัคร
สมาชิกเองผ่านฟอร์ม (ไม่ผ่าน LDAP) จำกัดให้เลือกได้แค่ student/lecturer/staff
เท่านั้น — role admin ต้องให้ผู้ดูแลระบบตั้งเองผ่าน backend เท่านั้น ป้องกัน
ไม่ให้ใครก็ได้สมัครแล้วได้สิทธิ์ admin เอง (นี่เป็นจุดที่เคยพบและแก้ช่องโหว่
ความปลอดภัยจริงระหว่างพัฒนา — ทดสอบยิง API ตรงพร้อมใส่ role=admin แล้วพบว่า
ผ่านได้ก่อนแก้ไข)

4.4 ลืมรหัสผ่าน (เฉพาะบัญชี Local)
--------------------------------------------
ใช้กลไก PasswordResetTokenGenerator ของ Django เอง (token หมดอายุอัตโนมัติ
เมื่อรหัสผ่านถูกเปลี่ยน ไม่ต้องสร้างตารางเก็บ token เพิ่มเอง) ส่งลิงก์รีเซ็ต
ทางอีเมลผ่าน Brevo บัญชีที่มาจาก LDAP จะได้รับข้อความแจ้งให้ติดต่อสำนัก
คอมพิวเตอร์ฯ แทน เพราะรหัสผ่าน LDAP ไม่ได้อยู่ในความควบคุมของระบบนี้


================================================================================
บทที่ 5: Flow การทำงานหลักของผู้ใช้ทั่วไป
================================================================================

5.1 ค้นหา/แนะนำห้อง
--------------------------------------------
ผู้ใช้กรอกเงื่อนไข: จำนวนผู้เข้าร่วม, วันที่/เวลา, อาคาร (ไม่บังคับ), อุปกรณ์
ที่ต้องการ (ไม่บังคับ) ระบบจะ:
  1) กรองห้องที่ความจุ (capacity) พอ และไม่ถูกจอง/ปิดซ่อม/ล็อกทั้งเทอมทับ
     ช่วงเวลาที่เลือก (ตรวจ 3 แหล่งพร้อมกัน: Booking, MaintenanceBlock,
     TermBooking)
  2) แนบผลพยากรณ์ AI (ถ้าห้องนั้นมีข้อมูล) เพื่อจัดอันดับ/แสดงสถานะสี
  3) เรียงผลลัพธ์ตามระดับ demand (ห้องที่ AI บอกว่า "ยังว่างชัวร์" ขึ้นก่อน
     ห้องที่ "กำลังจะเต็ม" เพื่อช่วยตัดสินใจเร็ว)

  นอกจากนี้ยังมีกล่องค้นหาด่วนที่ header — พิมพ์ชื่อห้องจะ fuzzy-match ชื่อ/
  อาคาร ส่วนพิมพ์ตัวเลขล้วนๆ (เช่น "40") ระบบตีความเป็น "จำนวนคน" แล้ว
  แนะนำห้องที่จุพอ เรียงจากพอดีที่สุดไปหาใหญ่กว่า

5.2 การจองรายวัน (Dynamic Booking)
--------------------------------------------
ผู้ใช้เลือกห้อง ใส่หัวข้อ/จำนวนคน/เวลา แล้วยืนยัน ระบบตรวจซ้อนอีกครั้งที่
ฝั่ง backend ณ วินาทีที่บันทึก (ดูหัวข้อ 5.4 เรื่อง race condition) สร้าง
Booking status='approved' ทันที (ไม่ต้องรอแอดมินอนุมัติสำหรับการจองรายวัน
ทั่วไป) ส่งอีเมลยืนยันพร้อมลิงก์ยกเลิกทันที และสร้าง Notification

5.3 การจองทั้งเทอม (Term Booking)
--------------------------------------------
ใช้สำหรับตารางเรียน/กิจกรรมที่ซ้ำทุกสัปดาห์ตลอดเทอม ผู้ใช้เลือกวันในสัปดาห์
+ ช่วงเวลา + วันเริ่ม/สิ้นสุดเทอม ระบบคำนวณวันที่จริงทั้งหมดที่จะเกิดขึ้น
(get_weekly_slots) แล้วตรวจ conflict กับทุกสัปดาห์พร้อมกัน (ไม่ใช่แค่
สัปดาห์แรก) ถ้าห้องเดิมไม่ว่างบางสัปดาห์ ระบบมีฟีเจอร์ "แนะนำแยกครึ่งเทอม"
(split_recommend / split_book) คือเสนอให้ใช้ห้อง A ครึ่งแรกของเทอม แล้ว
สลับไปห้อง B ครึ่งหลัง ถ้าไม่มีห้องเดียวที่ว่างตลอดทั้งเทอม

5.4 การป้องกันการจองซ้อน (Concurrency / Race Condition Prevention)
--------------------------------------------
จุดสำคัญทางเทคนิคที่มักถูกถาม: การเช็คห้องว่างที่ฝั่ง serializer (validate())
เป็นแค่การอ่านข้อมูล (read) เฉยๆ ถ้ามี 2 คนกดจองห้องเดียวกันเวลาเดียวกัน
พร้อมกันเป๊ะๆ ทั้งคู่อาจอ่านเห็นว่า "ว่าง" พร้อมกันแล้วจองซ้อนได้ (classic
race condition) วิธีแก้ในระบบนี้: ใช้ database row-level lock
(`Room.objects.select_for_update()`) ล็อกแถวของห้องนั้นไว้ก่อนเช็ค conflict
ภายใน database transaction (`transaction.atomic()`) — request ที่มาทีหลัง
ต้องรอ request แรก commit เสร็จก่อน จึงจะเช็ค conflict ต่อได้ (ซึ่งตอนนั้น
ข้อมูลอัปเดตแล้ว จะเจอว่าไม่ว่างจริง) การจองจึงถูก "เรียงคิว" ให้ทำทีละคำขอ
ต่อห้องเดียวกันโดยอัตโนมัติ ไม่ใช่ปล่อยให้ทั้งคู่ผ่านพร้อมกัน

5.5 การยกเลิกผ่านอีเมล (Cancel via Email Link)
--------------------------------------------
ทุกการจองมี checkin_token (UUID สุ่มไม่ซ้ำ) ฝังอยู่ในลิงก์ยกเลิก/เช็คอินที่
ส่งไปในอีเมลยืนยัน ผู้ใช้กดลิงก์ได้เลยโดยไม่ต้องล็อกอิน (endpoint ตรวจแค่ว่า
token ตรงกับที่บันทึกไว้หรือไม่) ออกแบบมาแทนกลไก "ต้องเช็คอินภายใน 15 นาที
ไม่งั้นถือว่า no-show" แบบเดิม ซึ่งถูกถอดออกไปแล้ว เพราะสร้างความกดดันเกินจำเป็น
ให้ผู้ใช้ที่มาสาย — เปลี่ยนมาเน้นให้ "ยกเลิกง่ายที่สุดถ้ามาไม่ได้" แทน

5.6 การแจ้งเตือนแบบ Real-time
--------------------------------------------
ทุกครั้งที่มี Notification ใหม่ถูกสร้างในฐานข้อมูล (เช่น แอดมินอนุมัติการจอง)
Django signal (post_save) จะส่งข้อความผ่าน Channels ไปยัง WebSocket group
เฉพาะของ user คนนั้น (`user_{id}_notifications`) ทันที ฝั่ง frontend
(กระดิ่งแจ้งเตือนที่ header) ที่เปิด WebSocket ค้างไว้จะได้รับ push ทันที
ไม่ต้อง refresh หรือ poll ถามซ้ำๆ


================================================================================
บทที่ 6: ระบบ AI พยากรณ์ความต้องการห้อง (หัวใจของงานวิจัย)
================================================================================

6.1 โจทย์ (Problem Formulation)
--------------------------------------------
พยากรณ์ "ปริมาณการใช้งานห้อง" (ชั่วโมงการจองรวมต่อวัน) ล่วงหน้า จากข้อมูล
การจองย้อนหลังของห้องนั้นเอง แล้วแปลงผลพยากรณ์เป็นระดับความต้องการ 4 ระดับ
(low/medium/high/urgent) เพื่อแสดงผลให้ผู้ใช้ตัดสินใจได้ง่าย นี่คือปัญหา
Time Series Forecasting ที่ปลายทางถูกใช้งานแบบ Classification (จัดกลุ่ม)

ตัวแปรเป้าหมาย (target, y): ผลรวมชั่วโมงการจอง (duration) ของห้องนั้นในแต่
ละวัน — ได้จากการขยาย (expand) รายการ Booking แต่ละรายการที่มี start_time/
end_time ให้กลายเป็นชั่วโมงต่อวัน แล้ว sum ต่อวันต่อห้อง ค่านี้ถูก clip ที่
เปอร์เซ็นไทล์ 95 ของห้องนั้นเพื่อลดผลกระทบจาก outlier (วันที่มีการจองผิดปกติ
เยอะมากๆ)

6.2 ข้อมูลที่ใช้ (Data Source)
--------------------------------------------
ใช้ข้อมูลการจองจริงในระบบ (Booking + TermBooking) ของแต่ละห้อง แปลงเป็น
Daily Time Series (1 แถว = 1 วัน = ผลรวมชั่วโมงใช้งานวันนั้น) ปัจจุบันมี 8
ห้องที่มีข้อมูลย้อนหลังมากพอสำหรับเทรนโมเดล AI จริง (ห้องอื่นในระบบยังจอง
ได้ปกติแต่ไม่มีการพยากรณ์กำกับ เพราะข้อมูลไม่พอ)

6.3 Feature Engineering (การสร้างตัวแปรนำเข้าโมเดล)
--------------------------------------------
จาก y ดิบ (ชั่วโมงต่อวัน) 1 คอลัมน์ ระบบสร้าง feature เพิ่มอีกหลายสิบตัว
แบ่งเป็นกลุ่ม:

  ก) ปฏิทิน/ฤดูกาล (Calendar features)
     - day of week, month, quarter, week_of_year, is_weekend, day_of_month
     - sin/cos ของคาบ 7 วัน (รายสัปดาห์) และ 365 วัน (รายปี) — ใช้ตัวแปร
       cyclic encoding แทนตัวเลขธรรมดา เพราะวันจันทร์กับวันอาทิตย์ที่ "ห่างกัน
       1 วัน" ในทางปฏิทิน ไม่ควรถูกโมเดลมองว่าห่างกันมากในเชิงตัวเลข

  ข) Lag features (ค่าย้อนหลัง)
     - lag_1, 2, 3, 7, 14, 21, 28 วัน (ค่าเมื่อวานจนถึงเมื่อ 4 สัปดาห์ก่อน)
     - lag_365 + ค่าเฉลี่ย/ค่าสูงสุดในหน้าต่าง ~15 วันรอบวันเดียวกันของปีก่อน
       (yoy_window_mean/max) — จับ pattern เหตุการณ์ประจำปี เช่น สัปดาห์สอบ
       ที่เกิดซ้ำช่วงเวลาใกล้เคียงกันทุกปีแต่ lag แค่ 28 วันมองไม่เห็น

  ค) Rolling statistics (สถิติเคลื่อนที่)
     - ค่าเฉลี่ย/ส่วนเบี่ยงเบนมาตรฐาน/สูงสุด/ต่ำสุด ในหน้าต่าง 3, 7, 14, 28
       วันย้อนหลัง (shift(1) ก่อนเสมอ กันไม่ให้ข้อมูลวันนั้นเองรั่วเข้าไปใน
       feature ของตัวเอง)
     - Exponentially Weighted Moving Average (ewm) ที่ span 3, 7, 14 วัน

  ง) Difference/Ratio features
     - diff_1, diff_7 (เปลี่ยนแปลงเทียบเมื่อวาน/สัปดาห์ก่อน)
     - pct_chg_7 (% เปลี่ยนแปลงเทียบสัปดาห์ก่อน)
     - ratio_vs_7d, ratio_vs_28d (ค่าล่าสุดเทียบสัดส่วนกับค่าเฉลี่ยระยะยาว)

  จ) Term booking features (เฉพาะระบบนี้ ไม่ใช่ feature ทั่วไปของ time
     series พยากรณ์ทั่วไป)
     - term_hours_day, term_sessions, in_term, days_until_term_end,
       term_progress_pct — เพราะการจองทั้งเทอมรู้ล่วงหน้าแน่นอนอยู่แล้ว (ไม่
       ต้องพยากรณ์ ต่างจากการจองรายวันที่ไม่แน่นอน) จึงใส่เป็น "ข้อมูลรู้
       ล่วงหน้า" (known future feature) ให้โมเดลใช้ประกอบการพยากรณ์ส่วนของ
       การจองรายวันที่เหลือได้แม่นขึ้น เช่น ถ้าช่วงนั้นมีคาบเรียนทั้งเทอม
       เต็มอยู่แล้ว โอกาสที่จะมีคนมาจองรายวันเพิ่มก็ย่อมต่างจากช่วงที่ห้อง
       ว่างจากตารางเทอม

  รวมทั้งหมดหลายสิบ feature ต่อ 1 แถว (1 วัน) — ก่อนเข้าโมเดลจะมีขั้นตอน
  คัดเลือก feature สำคัญ (feature selection บน train set เท่านั้น) เพื่อลด
  อัตราส่วน feature ต่อจำนวนแถวข้อมูล ป้องกันไม่ให้โมเดลเรียนรู้จาก noise
  ในข้อมูลที่มีจำนวนแถวค่อนข้างน้อยต่อห้อง (ไม่กี่ร้อยแถว)

6.4 สถาปัตยกรรมโมเดล — Ensemble 3 โมเดล
--------------------------------------------
ระบบไม่ได้ใช้โมเดลเดียว แต่ใช้ 3 โมเดลที่มีจุดแข็งต่างกัน แล้วรวมผล
(ensemble) ต่อห้อง 1 ชุด (แต่ละห้องมีชุดโมเดลของตัวเอง ไม่ใช้โมเดลร่วมกัน
ข้ามห้อง เพราะแต่ละห้องมี pattern การใช้งานต่างกัน):

  1) LSTM (Long Short-Term Memory) — Deep Learning
     สถาปัตยกรรม (ปัจจุบัน หลังปรับลดจากเวอร์ชันแรก):
        LSTM(48 units, return_sequences=False)
          -> Dropout(0.2)
          -> Dense(16, activation='relu')
          -> Dense(1)
     - Input เป็น multivariate sequence (ทุก feature ต่อ timestep ไม่ใช่แค่
       y ตัวเดียว) ความยาว lookback ต่างกันตามชุดทดลอง (20-90 วันย้อนหลัง)
     - Optimizer: Adam (learning_rate=0.0005, clipvalue=1.0 กันไม่ให้
       gradient ระเบิด)
     - Loss: MAE (Mean Absolute Error)
     - Scaling: ใช้ MinMaxScaler แยก 2 ตัว (ตัวหนึ่ง scale input X อีกตัว
       scale target y) และ fit scaler จากข้อมูล train เท่านั้น — ไม่ให้เห็น
       ข้อมูล validation/test ตอน fit เพื่อกัน data leakage
     - หมายเหตุสำคัญ: เดิมเคยลองสถาปัตยกรรมที่ใหญ่กว่านี้มาก (3 ชั้น LSTM
       128→64→32 units) แต่พบว่า overfit และแกว่งรุนแรงบนข้อมูลรายห้องที่มี
       แค่ไม่กี่ร้อยแถว (deep learning ต้องการข้อมูลจำนวนมากถึงจะแสดง
       ศักยภาพเหนือกว่าโมเดลอื่นได้จริง) จึงปรับลดเหลือโครงสร้างเล็กลงมาก
       (ชั้นเดียว 48 units) เพื่อให้ converge นิ่งกว่าบนข้อมูลขนาดเล็ก — เป็น
       การตัดสินใจที่ตั้งใจ ไม่ใช่ความผิดพลาด (trade-off ระหว่าง capacity
       กับ overfitting)

  2) LightGBM — Gradient Boosting (tree-based)
     โมเดลตระกูล Gradient Boosted Decision Trees ที่ Microsoft พัฒนา เร็ว
     และมักทำงานได้ดีกับ tabular data ขนาดเล็ก-กลาง (ตรงข้ามกับ deep
     learning ที่ต้องการข้อมูลเยอะ) — เหมาะกับข้อมูลรายห้องที่มีจำนวนแถว
     จำกัดในระบบนี้

  3) XGBoost — Gradient Boosting (tree-based) อีกตัว
     หลักการคล้าย LightGBM แต่ implementation/regularization ต่างกัน ใช้คู่
     กันเพื่อเป็น "เสียงที่สอง" ถ้า LightGBM พลาดในบาง pattern XGBoost อาจ
     จับได้ต่าง ลดความเสี่ยงจากจุดอ่อนของโมเดลเดียว

6.5 การรวมผล (Ensemble Weighting) — จุดที่มักถูกถามลึก
--------------------------------------------
ไม่ได้ใช้สัดส่วนคงที่ตายตัว แต่คำนวณน้ำหนักของแต่ละโมเดล "ต่อห้อง" จากผล
งานจริงบนชุดข้อมูล calibration (ชุดข้อมูลที่กันไว้ต่างหาก ไม่ใช่ train
ไม่ใช่ test):

  ขั้นที่ 1 — Prior เริ่มต้น (ค่าตั้งต้นก่อนเห็นผลจริง)
     LSTM 30% / LightGBM 45% / XGBoost 25%
     (ตั้งค่าเริ่มต้นแบบนี้เพราะคาดว่า LightGBM น่าจะทำงานดีที่สุดโดยเฉลี่ย
     บนข้อมูลขนาดเล็กแบบนี้ แต่ค่านี้เป็นแค่จุดตั้งต้น ไม่ใช่ค่าสุดท้าย)

  ขั้นที่ 2 — ปรับตามคะแนนจริง
     คำนวณ R² (สัดส่วนความแปรปรวนที่โมเดลอธิบายได้) และ MAE ของแต่ละโมเดล
     บนชุด calibration แล้วให้คะแนน = (R² ที่ไม่ติดลบ) / MAE — โมเดลที่แม่น
     กว่า (MAE ต่ำ) และอธิบายความแปรปรวนได้ดีกว่า (R² สูง) จะได้คะแนนสูงกว่า
     ถ้า LSTM มี R² ติดลบ (แปลว่าทำนายแย่กว่าการเดาค่าเฉลี่ยเฉยๆ) จะถูกตัด
     น้ำหนักเหลือ 0% ทันที ไม่ปล่อยให้ฉุดผลรวมลง

  ขั้นที่ 3 — Winner-take-all (ถ้าโมเดลเดียวชนะชัดเจน)
     ถ้าพบว่าโมเดลใดโมเดลหนึ่งให้ผลดีกว่าค่า ensemble แบบผสมอย่างชัดเจนบน
     calibration set ระบบจะให้น้ำหนัก 100% กับโมเดลนั้นเลย แทนที่จะผสม
     เฉลี่ยเสมอไป (ไม่ใช่ทุกห้องจะได้ผลจากการผสมโมเดลดีกว่าใช้โมเดลเดียว)

  ผลลัพธ์จริงที่พบจากการทดลอง: LSTM แทบไม่เคยชนะเลยในทางปฏิบัติ (น้ำหนัก
  เฉลี่ยออกมา 0% ในทุกชุดการทดลอง A-E) — LightGBM กับ XGBoost แย่งกันเป็น
  ผู้ชนะแทน สัดส่วนเปลี่ยนไปตามชุด hyperparameter (เช่น ชุด A ~62% LGB /
  38% XGB, ชุด E ~12% LGB / 88% XGB) สาเหตุที่เป็นไปได้: ข้อมูลรายห้องมี
  ขนาดเล็ก (ไม่กี่ร้อยแถว) เหมาะกับโมเดลตระกูล tree-based มากกว่า deep
  learning ที่ปกติต้องการข้อมูลจำนวนมากกว่านี้มากถึงจะแสดงศักยภาพเหนือกว่า
  ได้จริง — นี่คือข้อค้นพบ (finding) ที่ตอบคำถามงานวิจัยได้ตรงๆ ว่า "โมเดล
  ไหนเหมาะกับข้อมูลขนาดนี้"

6.6 วิธีแบ่งข้อมูล Train / Calibration / Test (สำคัญมาก มักถูกถาม)
--------------------------------------------
เนื่องจากเป็นข้อมูล Time Series ห้ามแบ่งแบบสุ่ม (random split) แบบที่ใช้กับ
ข้อมูลทั่วไป เพราะจะทำให้ข้อมูล "อนาคต" หลุดไปอยู่ใน training set ปนกับ
"อดีต" (data leakage เชิงเวลา) — ระบบนี้จึงแบ่งแบบเรียงตามเวลา (time-based
split) ไม่สลับลำดับ:

  - Train: 70% แรกของข้อมูล (เรียงตามเวลา เก่าสุดถึงกลางๆ)
  - Calibration: ถัดมา 10% (ใช้เลือก threshold และคำนวณ ensemble weight —
    ไม่ใช้เทรนโมเดลโดยตรง)
  - Test: 20% สุดท้าย (ข้อมูลใหม่สุด ไม่เคยถูกเห็นตอนเทรนหรือ calibrate เลย
    — ใช้วัดผลจริงเท่านั้น)

  ขั้นต่ำต้องมีข้อมูลอย่างน้อย 15 แถว (MIN_TRAIN_ROWS) ถึงจะเทรนได้ ถ้าห้อง
  ไหนข้อมูลไม่พอ ระบบจะข้ามห้องนั้นไปเลย ไม่สร้างข้อมูลปลอมมาแทน (no
  synthetic data augmentation)

6.7 การแปลงค่าพยากรณ์ (ตัวเลขต่อเนื่อง) เป็นระดับความต้องการ (Classification)
--------------------------------------------
โมเดลทั้ง 3 ตัวเป็น Regression (ทำนายตัวเลขต่อเนื่อง = ชั่วโมงการใช้งาน) แต่
สิ่งที่ผู้ใช้เห็นในแอปเป็นป้าย 4 ระดับ (low/medium/high/urgent →
🟢ยังว่าง/🟡ควรจอง/🟠รีบจอง/🔴ควรจองตอนนี้เลย) การแปลงทำโดย:

  1) Normalize ค่าที่ทำนายได้ ด้วยการหารด้วย peak_ref (เปอร์เซ็นไทล์ 95 ของ
     ค่าการใช้งานจริงในอดีตของห้องนั้น) ได้ค่า 0-1
  2) เทียบกับ threshold 2 ค่า (thr_high, thr_med) ที่คำนวณแบบ adaptive
     เฉพาะห้องนั้น (ไม่ใช้ค่าคงที่ตายตัวเดียวกันทุกห้อง) เพราะห้องที่ถูกใช้
     งานหนักอยู่แล้วเป็นปกติ กับห้องที่แทบไม่มีคนใช้ ควรมีเกณฑ์ "สูง"/"ต่ำ"
     ที่ต่างกัน ไม่ใช่ตัดที่ตัวเลขเดียวกันหมด
  3) ได้ label 3 กลุ่มหลักจากตัว classifier ภายใน (low/medium/urgent) แล้ว
     ชั้น business logic (views.py) ขยายรายละเอียดต่อเป็น 4 สถานะที่แสดงผล
     จริง โดยอิงค่า predicted_demand แบบละเอียดกว่าอีกชั้น (แบ่งช่วงที่
     0.30 / 0.50 / 0.70)

  ค่า Accuracy ที่รายงาน (เช่น "91%") จึงหมายถึง classification accuracy
  บนป้าย 3 กลุ่มนี้ (ทายกลุ่มถูก/ผิด) ไม่ใช่ค่าความแม่นของตัวเลขต่อเนื่อง
  โดยตรง (นั่นจะวัดด้วย R²/MAE แทน ซึ่งก็มีรายงานคู่กันในโค้ด)

6.8 การทดลองปรับ Hyperparameter (ชุด A-E) และผลลัพธ์
--------------------------------------------
ทดลองปรับความ "หนัก" ของการเทรนเป็น 5 ระดับ (A เบาสุด, E หนักสุด) เพื่อหา
จุดสมดุลระหว่างความแม่นกับการ overfit:

  ชุด | LSTM epoch/batch/lookback | LGB/XGB estimators/depth/lr
  A   | 10 / 16 / 20 วัน          | 10 ต้น, depth 6/5, lr 0.30 (เบาสุด)
  B   | 20 / 8  / 40 วัน          | 20 ต้น, depth 8/6, lr 0.12
  C   | 30 / 8  / 60 วัน          | 30 ต้น, depth 10/8, lr 0.08
  D   | 40 / 8  / 70 วัน          | 40 ต้น, depth 12/10, lr 0.0525 (ทดลอง)
  E   | 50 / 8  / 90 วัน          | 50 ต้น, depth 14/12, lr 0.036 (หนักสุด)

  ผล Train Accuracy เทียบ Test Accuracy:
  ชุด | Train Acc | Test Acc | ส่วนต่าง (overfitting gap)
  A   | 95.45%    | 91.14%   | 4.3 จุด   <- gap แคบสุด บาลานซ์ที่สุด
  B   | 96.63%    | 90.06%   | 6.6 จุด
  C   | 97.64%    | 91.06%   | 6.6 จุด
  D   | 98.01%    | 91.26%   | 6.8 จุด   <- test accuracy สูงสุด
  E   | 97.95%    | 90.92%   | 7.0 จุด   <- gap กว้างสุด

  บทสรุปจากการทดลอง: Test accuracy ของทุกชุดใกล้เคียงกันมาก (90-91.3%)
  แม้จะเทรนหนักขึ้นมากก็ตาม แต่ยิ่งเทรนหนักขึ้น (C/D/E) ช่องว่างระหว่าง
  train กับ test ยิ่งกว้างขึ้นเรื่อยๆ — สะท้อนว่าโมเดล "จำ" ข้อมูลเทรนได้
  เก่งขึ้น แต่ไม่ได้ generalize (ทำนายข้อมูลใหม่) ดีขึ้นตามจริง นี่คือ
  หลักฐานของ diminishing returns / overfitting risk ที่เพิ่มขึ้นเมื่อ
  เทรนหนักเกินจุดที่เหมาะสม

  ข้อสรุปเชิงปฏิบัติ: ถ้าเน้นความเสถียร/พร้อมใช้งานจริง (production) ชุด A
  บาลานซ์ที่สุด (แม่นใกล้เคียงชุดอื่นแต่ overfit น้อยสุด ใช้เวลาเทรนน้อย
  สุดด้วย) ถ้าเน้น test accuracy สูงสุดเพียงอย่างเดียวโดยไม่สนเวลาเทรน
  ชุด D ให้ผลดีที่สุด — งานวิจัยนี้แสดงให้เห็นว่า "เทรนนานขึ้น/ลึกขึ้น" ไม่ได้
  แปลว่า "แม่นขึ้นเสมอ" เกินจุดหนึ่ง

6.9 เทียบกับ Baseline — โมเดลดีกว่า "ทายมั่วๆ" จริงไหม (คำนวณจริง ไม่ใช่คาดเดา)
--------------------------------------------
คำถามที่กรรมการเกือบทุกคนถาม: "Accuracy 90% ดีจริงไหม เทียบกับอะไร" คำตอบ
ที่ดีที่สุดคือมีตัวเลขเปรียบเทียบจริงติดมือ ไม่ใช่พูดลอยๆ — จึงคำนวณ Naive
Baseline เพิ่มเติม (ใช้วิธี "Persistence": ทำนายว่าพรุ่งนี้จะเหมือนเมื่อวาน
เป๊ะๆ — เป็น baseline มาตรฐานที่สุดของงาน time series forecasting ที่ต้อง
เทียบด้วยเสมอ) โดยรันบนชุด Test เดียวกันเป๊ะ ใช้ threshold ชุดเดียวกันกับที่
โมเดลจริงใช้ (จาก meta.pkl ของชุด A) เพื่อให้เทียบกันได้ตรงไปตรงมา:

  ห้อง         | Naive (persistence) Accuracy | R²      | MAE
  2C05-06      | 59.4%                         | -0.177  | 2.60 ชม.
  2C09         | 63.0%                         | -0.420  | 2.79 ชม.
  2C10-11      | 54.9%                         | -0.194  | 2.92 ชม.
  2C16-17      | 55.3%                         | -0.249  | 3.18 ชม.
  3C05-06      | 50.5%                         |  0.013  | 3.03 ชม.
  1C-MEETING   | 96.7% (*)                     | -0.785  | 0.26 ชม.
  3C16-17      | 72.8%                         |  0.149  | 2.57 ชม.
  4C05         | 66.8%                         | -0.651  | 1.45 ชม.
  เฉลี่ยรวม     | 64.9%                         | ส่วนใหญ่ติดลบ | -

  (*) ห้อง 1C-MEETING แทบไม่ถูกใช้งานเลย (ส่วนใหญ่เป็น 0 ชม./วัน) ทำให้
  "เมื่อวาน=พรุ่งนี้" ถูกบ่อยโดยบังเอิญเพราะข้อมูลเอียงไปทาง "ต่ำ" เกือบ
  ตลอด (class imbalance) — accuracy สูงจากกรณีนี้จึงไม่ได้แปลว่า baseline
  ทำนายเก่ง สังเกตว่า R² ของห้องนี้ยังติดลบหนักอยู่ดี (-0.785) ซึ่งเป็น
  หลักฐานว่า accuracy อย่างเดียวโกหกได้ ต้องดู R²/MAE ประกอบเสมอ — นี่คือ
  เหตุผลที่รายงานผลของโมเดลจริงในเอกสารนี้ก็ใส่ทั้ง accuracy, F1, R², MAE
  ไว้ด้วยกันเสมอ ไม่ใช่โชว์แค่ accuracy ตัวเดียว

  สรุปผลเทียบ: โมเดล ensemble จริง (ชุด A) ได้ Test Accuracy เฉลี่ย 91.14%
  เทียบกับ naive persistence baseline ที่ 64.9% — สูงกว่า baseline ~26.2
  จุดเปอร์เซ็นต์ และที่สำคัญกว่านั้น R² ของโมเดลจริงเป็นบวกในทุกห้อง (โมเดล
  อธิบายความแปรปรวนได้จริง) ในขณะที่ baseline ส่วนใหญ่ R² ติดลบ (แย่กว่า
  การเดาค่าเฉลี่ยเฉยๆ) — เป็นหลักฐานเชิงปริมาณที่ชัดเจนว่าโมเดลเรียนรู้
  pattern ที่มีความหมายจริง ไม่ได้อาศัยแค่ความเอียงของข้อมูล (class
  imbalance) เหมือน baseline

6.10 การพยากรณ์สำหรับห้องข้อมูลน้อย (Cold Start)
--------------------------------------------
ห้องที่เพิ่งเปิดใช้งานยังไม่มีประวัติมากพอเทรนโมเดลเฉพาะตัว ระบบมีกลไก
SeasonalMedianModel เป็น fallback — รวมข้อมูล daily series จากห้องประเภท
เดียวกัน (room_type เดียวกัน) มาสร้างเป็น "prior" (ค่าฐานเริ่มต้น) ให้ห้อง
ใหม่ยืมใช้ชั่วคราว จนกว่าจะสะสมข้อมูลของตัวเองมากพอ

9.1 หมวดวิธีการ AI/ML (Methodology)
--------------------------------------------------------------------------------

Q: ทำไมต้องใช้ 3 โมเดลรวมกัน ทำไมไม่ใช้โมเดลเดียว?
A: เพราะแต่ละโมเดลมีจุดแข็งต่างกัน และไม่มีโมเดลไหนชนะทุกกรณีเสมอไป การรวม
   (ensemble) แบบให้น้ำหนักตามผลงานจริงต่อห้อง ช่วยลดความเสี่ยงจากจุดอ่อน
   ของโมเดลเดียว — ผลทดลองจริงก็ยืนยันด้วยว่าห้องต่างกันมีโมเดลที่ชนะต่าง
   กัน (บางห้อง LightGBM ชนะ บางห้อง XGBoost ชนะ)

Q: ทำไม LSTM ถึงแทบไม่ชนะเลย ทำไมยังเก็บไว้ในระบบ?
A: ข้อมูลรายห้องมีขนาดเล็ก (ไม่กี่ร้อยแถว) ซึ่งเป็นขนาดที่ deep learning
   มักไม่ได้เปรียบ tree-based model เท่าที่ควร (deep learning ต้องการข้อมูล
   จำนวนมากกว่านี้มากถึงจะแสดงศักยภาพได้เต็มที่) — แต่ยังเก็บ LSTM ไว้ใน
   ระบบเพราะ (1) ระบบ ensemble ออกแบบมาให้ตัดน้ำหนัก LSTM เหลือ 0% อัตโนมัติ
   เมื่อมันทำงานแย่ ไม่กระทบผลลัพธ์สุดท้าย (2) ถ้าในอนาคตสะสมข้อมูลมากขึ้น
   เรื่อยๆ LSTM มีโอกาสเริ่มแสดงศักยภาพได้ (3) เป็นข้อค้นพบเชิงวิจัยที่มีค่า
   ในตัวเอง ว่าขนาดข้อมูลส่งผลต่อการเลือกโมเดลอย่างไร

Q: ป้องกัน Data Leakage ยังไงบ้าง?
A: สามชั้น: (1) แบ่ง train/calibration/test แบบเรียงเวลา ไม่สุ่ม กันอนาคต
   หลุดเข้าไปในอดีต (2) fit scaler (MinMaxScaler) จากข้อมูล train เท่านั้น
   ไม่ใช้ข้อมูล validation/test มา fit (3) feature ที่เป็น rolling
   statistics ทุกตัว shift(1) ก่อนเสมอ กันไม่ให้ค่าของวันนั้นเองรั่วเข้าไป
   ในการคำนวณ feature ของตัวมันเอง

Q: ทำไมแบ่ง Train/Test แบบ Time-based ไม่ใช้ Random Split ธรรมดาแบบ
   scikit-learn ปกติ?
A: เพราะข้อมูลเป็น Time Series ที่มีความสัมพันธ์เชิงเวลา (autocorrelation)
   ถ้าสุ่มแบ่งแบบธรรมดา โมเดลจะได้เห็นข้อมูล "อนาคต" ปนอยู่ใน training set
   ทำให้ผลวัดดูดีเกินจริง (data leakage) แต่ใช้งานจริงจะพยากรณ์แย่กว่าที่
   วัดได้มาก เพราะสถานการณ์จริงไม่มีทางรู้อนาคตล่วงหน้า

Q: Accuracy 90% ที่รายงาน วัดจากอะไร แม่นจริงหรือไม่ เทียบกับอะไร?
A: วัดจาก classification accuracy บนป้าย 3 ระดับ (low/medium/urgent) ที่
   แปลงมาจากค่าพยากรณ์ต่อเนื่อง โดยเทียบกับป้ายจริงบนชุด Test (20% สุดท้าย
   ที่โมเดลไม่เคยเห็นระหว่างเทรน) วัดแบบยุติธรรมเพราะ threshold ที่ใช้แปลง
   ค่าเป็นป้ายก็คำนวณจากชุด calibration แยกต่างหาก ไม่ใช่ปรับ threshold ให้
   เข้ากับผล test ทีหลัง (ซึ่งจะทำให้ตัวเลข "โกงสวย" ได้) — และเทียบกับ
   naive persistence baseline ("พรุ่งนี้เหมือนเมื่อวาน") ที่คำนวณจริงแล้วได้
   เฉลี่ยแค่ 64.9% (ดูตารางเต็มในหัวข้อ 6.9) โมเดลจริงสูงกว่า ~26 จุด และ
   R² เป็นบวกทุกห้อง (baseline ส่วนใหญ่ R² ติดลบ) เป็นหลักฐานว่าโมเดลเรียนรู้
   pattern จริง ไม่ได้อาศัยความเอียงของข้อมูล

Q: ทำไมรายงานทั้ง Accuracy, F1, R², MAE พร้อมกัน ไม่ใช้ตัวเดียว?
A: เพราะแต่ละตัวชี้ปัญหาคนละมุม accuracy อย่างเดียวหลอกได้ง่ายเมื่อข้อมูล
   เอียง (class imbalance) — เห็นได้จากห้อง 1C-MEETING ที่ naive baseline
   ได้ accuracy สูงถึง 96.7% ทั้งที่ R² ติดลบหนัก (-0.785) เพราะห้องนั้น
   แทบไม่มีคนใช้เลย ทายว่า "ว่างตลอด" ก็ถูกบ่อยโดยบังเอิญ ไม่ได้แปลว่า
   โมเดลเก่ง — F1 ช่วยดูสมดุลระหว่าง precision/recall ในแต่ละคลาส ส่วน
   R²/MAE วัดที่ตัวเลขต่อเนื่องจริง (ไม่ผ่านการหั่นเป็นกลุ่ม) จึงต้องดู
   ทั้งชุดประกอบกันเสมอ

Q: Threshold (thr_high, thr_med) ที่ใช้แบ่งกลุ่ม low/medium/urgent มาจาก
   ไหน ทำไมไม่ตั้งตายตัว เช่น 0.3/0.6/0.9 เท่ากันทุกห้อง?
A: คำนวณแบบ adaptive จาก percentile ของค่าการใช้งานจริงในอดีตของห้องนั้น
   เอง (peak_ref = เปอร์เซ็นไทล์ 95) เพราะห้องที่ถูกใช้งานหนักเป็นปกติอยู่
   แล้ว กับห้องที่แทบไม่มีคนใช้ ควรมีเกณฑ์ "สูง"/"ต่ำ" ที่ต่างกัน ถ้าใช้
   ค่าคงที่เดียวกันทุกห้อง ห้องที่ใช้งานน้อยจะไม่มีวันถูกจัดเป็น "urgent"
   เลย ทั้งที่เทียบกับพฤติกรรมปกติของห้องนั้นเองมันอาจจะสูงผิดปกติจริงๆ

Q: ทำไมต้องมีขั้น Calibration แยกจาก Test มี Train กับ Test สองชุดพอไหม?
A: Calibration set ใช้สำหรับตัดสินใจ 2 อย่างที่ "ไม่ควร" ตัดสินใจจากข้อมูล
   Test เอง คือ (1) เลือกน้ำหนัก ensemble ต่อโมเดล และ (2) อ้างอิงหา
   threshold การจัดกลุ่ม ถ้าใช้ข้อมูล Test มาช่วยตัดสินใจสองอย่างนี้ด้วย
   จะกลายเป็นการ "แอบดูเฉลย" ก่อนสอบ (indirect leakage) ทำให้ตัวเลข Test
   Accuracy ที่รายงานดูดีเกินจริง Calibration set จึงทำหน้าที่เป็น
   "สนามซ้อม" ก่อนเจอข้อสอบจริง (Test) ซึ่งเห็นแค่ครั้งเดียวตอนวัดผล

Q: ทำไมไม่ทำ K-Fold Cross Validation เพื่อความน่าเชื่อถือทางสถิติ?
A: K-Fold แบบมาตรฐาน (สุ่มแบ่งเป็น K ส่วนแล้วสลับกันเป็น validation) ใช้ไม่
   ได้ตรงๆ กับข้อมูล Time Series เพราะจะทำให้บาง fold มีข้อมูลอนาคตอยู่ใน
   training ของ fold อื่น (data leakage เชิงเวลาแบบเดียวกับที่กล่าวไปข้างต้น)
   ถ้าจะทำอย่างถูกต้องต้องใช้ Time Series Cross Validation (walk-forward /
   expanding window) ซึ่งเป็นข้อจำกัดที่ยอมรับตรงๆ ของงานนี้ (ดูบทที่ 10
   ข้อจำกัด) — ปัจจุบันวัดผลจาก 1 split เดียว ยังไม่ได้ทำหลาย fold เพื่อดู
   ความแปรปรวนของผลลัพธ์

Q: ทำไมใช้ MAE เป็น loss function ของ LSTM ไม่ใช้ MSE?
A: MAE (Mean Absolute Error) ทนต่อ outlier ได้ดีกว่า MSE (Mean Squared
   Error) เพราะ MSE ยกกำลังสองค่าความคลาดเคลื่อน ทำให้วันที่มีการจองผิดปกติ
   สูงมากๆ (outlier) ส่งผลกระทบต่อการเรียนรู้ของโมเดลรุนแรงเกินจำเป็น
   ข้อมูลการจองห้องมีแนวโน้มมี outlier แบบนี้ได้ (เช่น วันจัดกิจกรรมพิเศษ)
   MAE จึงเหมาะกว่าในบริบทนี้ (โค้ดยังมีทางเลือก Huber loss ไว้ด้วยสำหรับ
   กรณี outlier รุนแรงกว่านี้ — robust กว่า MAE ธรรมดาอีกขั้น)

Q: ทำไมต้อง clip ข้อมูลที่เปอร์เซ็นไทล์ 95 ก่อนเทรน?
A: ลดผลกระทบจากวันที่มีค่าผิดปกติสูงมากๆ (เช่น error ในการบันทึกข้อมูล
   หรือเหตุการณ์พิเศษที่ไม่ใช่ pattern ปกติ) ไม่ให้ไปดึงการเรียนรู้ของโมเดล
   ให้เอนเอียงเพื่อ "จำ" ค่าสุดโต่งไม่กี่จุดจนเสียความแม่นกับข้อมูลส่วนใหญ่
   ที่เป็น pattern ปกติ เป็นเทคนิค standard ของงาน forecasting ที่มี noise

Q: log-transform (use_log) ใช้ตอนไหน ทำไมไม่ใช้กับทุกห้องเหมือนกันหมด?
A: ใช้เฉพาะห้องที่ข้อมูลมีลักษณะเบ้ขวารุนแรง (right-skewed — ส่วนใหญ่ค่า
   น้อย มีบางวันค่าสูงกระโดด) การแปลง log ช่วยให้การกระจายตัวสมมาตรขึ้น
   โมเดลเรียนรู้ง่ายขึ้น แต่ถ้าห้องที่ข้อมูลกระจายตัวปกติอยู่แล้วบังคับใช้
   log จะทำให้เสียรายละเอียดเปล่าๆ จึงตัดสินใจต่อห้อง (data-driven) ไม่ใช่
   ตั้งค่าตายตัว

--------------------------------------------------------------------------------
9.2 หมวดสถาปัตยกรรมซอฟต์แวร์ (Software Architecture)
--------------------------------------------------------------------------------

Q: ระบบจองห้องซ้อนกันได้ไหม ป้องกันยังไง?
A: ป้องกันด้วย database row lock (select_for_update) ภายใน transaction
   บังคับให้คำขอจองห้องเดียวกันถูกประมวลผลทีละคำขอ (serialize) ไม่ใช่ปล่อย
   ให้สองคำขอพร้อมกันผ่านการเช็คพร้อมกันได้

Q: ทำไมใช้ LDAP แทนระบบสมัครสมาชิกทั่วไป?
A: เพื่อผูกกับบัญชีจริงของมหาวิทยาลัยที่มีอยู่แล้ว ลดภาระผู้ใช้ (ไม่ต้อง
   สมัครบัญชีใหม่) และยืนยันตัวตนที่น่าเชื่อถือกว่า (ผ่านฐานข้อมูลกลางของ
   มหาวิทยาลัย) ระบบยังคงเปิดทางบัญชี local ไว้สำหรับกรณีที่ไม่มีบัญชี LDAP
   (fallback)

Q: ทำไมใช้ WebSocket แทนการ poll (เรียก API ซ้ำๆ ทุกกี่วินาที)?
A: WebSocket เปิด connection ค้างไว้ ให้ server ส่งข้อมูล push มาทันทีที่
   มีเหตุการณ์เกิดขึ้นจริง ประหยัด resource กว่ามาก (ไม่ต้องยิง request ซ้ำๆ
   ทุกไม่กี่วินาทีทั้งที่ส่วนใหญ่ไม่มีอะไรเปลี่ยน) และให้ผู้ใช้เห็นการ
   เปลี่ยนแปลงแบบทันทีจริงๆ (real-time) ไม่ใช่ล่าช้าตามรอบ poll

Q: ถ้าข้อมูลห้องมีน้อยเทรนโมเดลไม่ได้ ทำยังไง?
A: มี MIN_TRAIN_ROWS (15 แถว) เป็นเกณฑ์ขั้นต่ำ ถ้าไม่ถึงจะข้ามห้องนั้นไปเลย
   ไม่สร้างข้อมูลปลอม (synthetic) มาแทน เพราะจะทำให้ผลพยากรณ์เชื่อถือไม่ได้
   สำหรับห้องใหม่ที่ยังไม่มีข้อมูลพอ ระบบมี SeasonalMedianModel เป็น
   fallback ชั่วคราว โดยยืมข้อมูลจากห้องประเภทเดียวกันมาเป็นฐาน

Q: ทำไมแยก Django กับ React เป็นคนละโปรเจกต์ ไม่ใช้ Django Template
   render หน้าเว็บไปเลย?
A: แยก concern ชัดเจนระหว่าง data/business logic (backend) กับ UX
   (frontend), React SPA ให้ประสบการณ์ลื่นกว่า (ไม่ reload ทั้งหน้าทุกครั้ง)
   และสำคัญที่สุดคือ backend เป็น REST API ล้วนๆ ทำให้ในอนาคตต่อกับแอปมือถือ
   หรือ client อื่นได้โดยไม่ต้องแก้ backend เลย

Q: ทำไมใช้ JWT แทน Session-based authentication แบบ Django ปกติ?
A: JWT เป็น stateless (server ไม่ต้องเก็บ session state ไว้) เหมาะกับ
   สถาปัตยกรรมที่ frontend/backend แยกคนละ origin/domain กันชัดเจนแบบนี้
   และรองรับ client หลายชนิดในอนาคต (เว็บ, มือถือ) ได้ง่ายกว่า session
   cookie ที่ผูกกับ domain เดียว

Q: ทำไมงานเบื้องหลัง (เตือนก่อนใช้ห้อง) ใช้ APScheduler ไม่ใช้ Celery ซึ่ง
   เป็นมาตรฐานมากกว่าสำหรับงานคิว (task queue)?
A: งานเบื้องหลังของระบบนี้เป็นงานเบาๆ ไม่ซับซ้อน (แค่ trigger ตามเวลา เช่น
   เช็คทุก 5 นาทีว่ามีการจองไหนใกล้ถึงเวลาแล้วส่งอีเมลเตือน) ไม่ต้องการ
   distributed task queue ที่ซับซ้อนแบบ Celery ซึ่งต้องมี message broker
   เพิ่ม (เช่น Redis/RabbitMQ) เป็น infrastructure เพิ่มเติมโดยไม่จำเป็น —
   APScheduler (แบบ DB-backed job store ผ่าน django-apscheduler) เบากว่า
   deploy ง่ายกว่า เหมาะกับสเกลปัจจุบันของระบบ

--------------------------------------------------------------------------------
9.3 หมวดความปลอดภัย (Security)
--------------------------------------------------------------------------------

Q: ป้องกัน SQL Injection ยังไง?
A: ใช้ Django ORM ตลอดทั้งระบบ ไม่มีการต่อ SQL string เองเลย ORM ของ Django
   ทำ parameterized query ให้อัตโนมัติทุก query จึงไม่เปิดช่องให้ SQL
   Injection ได้ตั้งแต่ต้น (ต่างจากการเขียน raw SQL แล้วต่อ string ผู้ใช้
   เข้าไปตรงๆ)

Q: ป้องกัน XSS (Cross-Site Scripting) ยังไง?
A: React escape ค่าที่ render ใน JSX โดยอัตโนมัติ (ค่าที่ผู้ใช้กรอกจะไม่ถูก
   ตีความเป็น HTML/JavaScript โดยตรง) ฝั่ง backend เองก็ไม่ได้ render HTML
   จาก input ผู้ใช้ตรงๆ ยกเว้นหน้ายืนยัน/ยกเลิกผ่านอีเมล (cancel-email) ซึ่ง
   เป็นหน้า HTML ที่ backend สร้างเอง ไม่ใช่เอา input ผู้ใช้มาแทรกดิบๆ

Q: รหัสผ่านเก็บยังไง ปลอดภัยแค่ไหน?
A: บัญชี local ใช้ Django password hasher มาตรฐาน (PBKDF2 + salt แบบ
   built-in ของ Django ไม่ได้เก็บ plain text หรือ hash เปล่าไม่มี salt)
   ส่วนบัญชี LDAP ไม่เก็บรหัสผ่านที่ใช้งานได้ในระบบนี้เลย (เรียก
   set_unusable_password() ไว้) เพราะตรวจสอบผ่าน LDAP server ของ
   มหาวิทยาลัยโดยตรงทุกครั้งที่ login

Q: ลิงก์ยกเลิก/เช็คอินผ่านอีเมล (ไม่ต้องล็อกอิน) ปลอดภัยไหม ใครก็เดา URL
   แล้วยกเลิกจองคนอื่นได้ไหม?
A: ใช้ UUID สุ่ม (checkin_token) เป็นกุญแจในลิงก์ ไม่ใช่เลข booking id
   ธรรมดาที่เดาต่อเนื่องได้ (เช่น id=101, 102, 103...) UUID v4 มีพื้นที่
   ความเป็นไปได้กว้างมาก (2^122 ค่า) เดามั่วให้ตรงในทางปฏิบัติถือว่าเป็นไป
   ไม่ได้ ผลกระทบที่สุดถ้า token หลุด (เช่น อีเมลถูกส่งต่อ) คือยกเลิกได้แค่
   การจองรายการเดียวนั้น ไม่กระทบบัญชีหรือข้อมูลอื่น

Q: เคยเจอช่องโหว่จริงระหว่างพัฒนาไหม แก้ยังไง?
A: เจอจริง 2 ครั้ง:

   ครั้งที่ 1 — Privilege Escalation ตอนสมัครสมาชิก: ฟอร์มสมัครสมาชิกเอง
   แต่เดิมไม่ได้ validate ค่า role ที่ส่งมา ทำให้ทดสอบยิง API ตรงพร้อมใส่
   role="admin" ในตอน register แล้วได้สิทธิ์ admin ทันทีโดยไม่ต้องผ่านการ
   อนุมัติจากใคร แก้โดยเพิ่ม validate_role() ใน serializer จำกัดให้สมัครเอง
   ได้แค่ 3 role (student/lecturer/staff) เท่านั้น role admin ต้องตั้งผ่าน
   backend/admin panel โดยผู้ดูแลระบบเท่านั้น — ทดสอบยิง exploit เดิมซ้ำ
   หลังแก้ยืนยันว่าถูกบล็อกจริง

   ครั้งที่ 2 — LDAP account bypass ตอนลืมรหัสผ่าน: โค้ดเดิมเช็คว่า "เป็น
   บัญชี LDAP หรือไม่" ด้วย `not user.password` (สมมติว่าฟิลด์นี้ว่างเปล่า
   เสมอสำหรับบัญชี LDAP) แต่ทดสอบจริงกับบัญชี LDAP ในฐานข้อมูลพบว่า
   `set_unusable_password()` ของ Django ไม่ได้ทำให้ฟิลด์นี้ว่างเปล่า แต่เก็บ
   เป็นสตริง `!<สุ่มอักขระ>` ซึ่งเป็นค่า truthy เสมอ — แปลว่าเงื่อนไขนี้
   `False` เสมอสำหรับบัญชี LDAP จริง ทำให้ระบบไหลผ่านไปส่งอีเมลรีเซ็ต
   รหัสผ่านให้บัญชี LDAP ได้ (ทั้งที่ไม่ควรทำได้) และถ้าทำจนจบ ผู้ใช้จะตั้ง
   รหัสผ่าน local จริงให้บัญชี LDAP ได้สำเร็จ กลายเป็นช่องทางเข้าระบบสำรอง
   ที่ไม่ได้ตั้งใจให้มี (unintended backdoor) แก้โดยเปลี่ยนไปเช็คด้วย
   `user.has_usable_password()` (API ที่ถูกต้องของ Django สำหรับกรณีนี้ —
   ที่จริงมีใช้ถูกต้องอยู่แล้วในอีกจุดหนึ่งของโค้ด คือ
   ChangePasswordSerializer แต่จุดนี้เขียนแยกกันคนละที่แล้วพลาดไม่ตรงกัน)
   ทดสอบยิง API จริงกับบัญชี LDAP ในฐานข้อมูลซ้ำหลังแก้ ยืนยันว่าได้ข้อความ
   "ติดต่อ IT" ที่ถูกต้องแล้ว ไม่ไหลผ่านไปส่งอีเมลอีกต่อไป

   บทเรียนร่วมของทั้งสองครั้ง: ช่องโหว่ทั้งคู่ไม่ใช่เรื่องซับซ้อนทางเทคนิค
   เลย แต่เกิดจาก "สมมติฐานที่ไม่ได้ตรวจสอบจริง" (ไม่ validate input /
   ไม่ตรวจสอบพฤติกรรมจริงของ API ที่เรียกใช้) วิธีจับได้ทั้งสองครั้งคือ
   ทดสอบยิง exploit จริง/ตรวจข้อมูลจริงในฐานข้อมูล ไม่ใช่แค่อ่านโค้ดแล้ว
   คิดว่าน่าจะถูก

Q: ป้องกัน CORS/CSRF ยังไง?
A: ตั้ง CORS_ALLOWED_ORIGINS ระบุ origin ของ frontend ที่อนุญาตชัดเจน
   (ไม่ได้เปิดกว้างรับทุก origin) ส่วน CSRF ความเสี่ยงต่ำกว่าระบบที่ใช้
   session cookie เพราะ API หลักยืนยันตัวตนด้วย JWT ที่แนบผ่าน Authorization
   header (ไม่ใช่ cookie ที่ browser แนบอัตโนมัติ) ซึ่งเป็นรูปแบบที่ CSRF
   โจมตีได้ยากกว่าโดยธรรมชาติ

--------------------------------------------------------------------------------
9.4 หมวดเปรียบเทียบกับวิธีอื่น (ทำไมไม่ใช้วิธีอื่น)
--------------------------------------------------------------------------------

Q: ทำไมไม่ใช้ ARIMA/SARIMA ซึ่งเป็นวิธี classical ของ time series
   forecasting?
A: ARIMA เหมาะกับ univariate series (พยากรณ์จากค่าประวัติของตัวมันเองล้วนๆ)
   และมักต้องการให้ข้อมูล stationary (ปรับ differencing เอง) งานนี้มี
   exogenous feature จำนวนมากที่อยากใช้ประกอบการพยากรณ์ (ตารางจองทั้งเทอม
   ที่รู้ล่วงหน้าแน่นอน, ปฏิทิน, equipment ฯลฯ) ซึ่ง ARIMA พื้นฐานผนวกรวม
   ตัวแปรเสริมพวกนี้ได้ไม่เป็นธรรมชาติเท่าโมเดลตระกูล ML ที่รับ tabular
   feature ได้ตรงๆ อยู่แล้ว (SARIMAX ทำได้แต่ซับซ้อนกว่าและยังเป็น linear
   model เป็นหลัก จับ non-linear pattern ได้จำกัดกว่า tree-based/deep
   learning)

Q: ทำไมไม่ใช้ Facebook Prophet ซึ่งออกแบบมาสำหรับงาน forecasting ที่มี
   seasonality โดยเฉพาะ?
A: Prophet เก่งเรื่อง trend/seasonality decomposition อัตโนมัติและใช้ง่าย
   แต่จำกัดความยืดหยุ่นในการผสาน feature เสริมแบบ tabular จำนวนมาก และ
   เป็นโมเดลเดี่ยว ไม่ได้ออกแบบมาให้ทำ ensemble กับโมเดลอื่นได้เป็นธรรมชาติ
   แบบที่งานนี้ต้องการ (เทียบ performance หลายโมเดลแล้วเลือก/ผสมที่ดีที่สุด
   ต่อห้อง)

Q: ทำไมไม่ใช้ Transformer (เช่น Temporal Fusion Transformer) ซึ่งเป็น
   state-of-the-art ของ time series ในปัจจุบัน?
A: Transformer ต้องการข้อมูลปริมาณมากกว่านี้มากถึงจะแสดงศักยภาพเหนือกว่า
   โมเดลที่เล็กกว่าได้จริง (ปกติหลักพัน-หมื่น sequence ขึ้นไป) ข้อมูลราย
   ห้องในงานนี้มีแค่ไม่กี่ร้อยแถวต่อห้อง — จากที่พบแล้วว่าแม้แต่ LSTM (deep
   learning ที่เล็กกว่า Transformer มาก) ยังแทบไม่ชนะ tree-based model บน
   ข้อมูลขนาดนี้ Transformer ที่มี parameter เยอะกว่ามากจะยิ่ง overfit
   รุนแรงกว่าเดิม ไม่เหมาะกับขนาดข้อมูลที่มีอยู่จริงในตอนนี้

Q: ทำไมไม่ใช้ Random Forest ธรรมดา ทำไมต้อง Gradient Boosting (LightGBM/
   XGBoost) โดยเฉพาะ?
A: Random Forest สร้างต้นไม้แบบอิสระจากกันแล้วเฉลี่ยผล (bagging) ส่วน
   Gradient Boosting สร้างต้นไม้ทีละต้นแบบเรียนรู้แก้ error ของต้นก่อนหน้า
   ต่อเนื่องกัน (boosting) ซึ่งมักให้ความแม่นสูงกว่าบนงาน tabular data
   ขนาดกลาง-เล็กเมื่อ tune ดีๆ และ LightGBM/XGBoost ทั้งสองมี regularization
   ในตัวที่ช่วยคุม overfitting ได้ดีกว่า Random Forest พื้นฐานด้วย

Q: เคยลองเทียบกับโมเดลอื่นจริงไหม หรือเลือกจากทฤษฎีอย่างเดียว?
A: การเปรียบเทียบเชิงประจักษ์ (empirical) ที่ทำจริงในงานนี้คือระหว่าง 3
   โมเดลที่ใช้งานอยู่ (LSTM vs LightGBM vs XGBoost) ผ่านกลไก ensemble
   weighting ซึ่งเปรียบเทียบให้อัตโนมัติทุกห้อง และการทดลอง hyperparameter
   5 ระดับ (A-E) — ส่วนวิธีอื่น (ARIMA/Prophet/Transformer/Random Forest)
   ยังไม่ได้ทดลองจริงในระบบนี้ เป็นการให้เหตุผลเชิงทฤษฎี/ข้อจำกัดของ
   ทรัพยากรข้อมูลที่มี เป็นข้อจำกัดที่ควรตอบตรงๆ (ดูบทที่ 10 และ 11)

--------------------------------------------------------------------------------
9.5 หมวดภาพรวม/กระบวนการทำงานวิจัย
--------------------------------------------------------------------------------

Q: งานวิจัยนี้มีส่วนไหนที่เป็น "ของใหม่/contribution" ไม่ใช่แค่เอาไลบรารีมา
   ต่อกัน?
A: (1) การออกแบบ ensemble weighting แบบ adaptive-per-room ที่คำนวณจากผล
   งานจริงบน calibration set ไม่ใช่สัดส่วนคงที่ (2) การทดลองเปรียบเทียบ
   hyperparameter 5 ระดับ (A-E) อย่างเป็นระบบ พิสูจน์ว่าเทรนหนักขึ้นไม่ได้
   แปลว่าดีขึ้นเสมอ พบจุดสมดุลที่เหมาะสม (3) การผสาน "known future
   feature" จากข้อมูลจองทั้งเทอมเข้ากับการพยากรณ์ demand รายวัน ซึ่งเป็น
   context เฉพาะของโดเมนนี้ (4) adaptive threshold ต่อห้องแทนเกณฑ์ตายตัว
   เดียวกันทุกห้อง (5) การวัดผลเทียบ naive baseline อย่างเป็นรูปธรรม
   (ไม่ใช่แค่รายงาน accuracy ลอยๆ)

Q: ทำไมเลือกทำหัวข้อนี้ (ระบบจองห้อง + AI พยากรณ์)?
A: เป็นปัญหาจริงที่หน่วยงานเจอ (ห้องมีจำกัด การจองแบบเดิมไม่มีข้อมูลช่วย
   ตัดสินใจ) และเปิดโอกาสให้ประยุกต์ทั้งงานด้านวิศวกรรมซอฟต์แวร์ (ระบบ
   จองแบบ real-time, ป้องกัน race condition) และงานด้าน Machine Learning
   (time series forecasting, ensemble learning) ในโปรเจกต์เดียว มีข้อมูล
   จริงจากการใช้งานจริงให้ทดลองด้วย ไม่ใช่ข้อมูลจำลอง

Q: ระบบนี้ผ่านการใช้งานจริงแล้วหรือยัง?
A: ตอบตามสถานะจริง ณ วันสอบ — ถ้ายังอยู่ในช่วงทดสอบ/เตรียมเปิดตัว ให้บอก
   ตรงๆ ว่าอยู่ระหว่างขั้นทดสอบ deploy แล้วบน Render/Neon พร้อมใช้งานจริง
   แต่ยังไม่เปิดให้ผู้ใช้จริงทั้งหมด (ถ้าสถานะเปลี่ยนไปแล้วตอนใกล้สอบ ให้
   อัปเดตคำตอบข้อนี้ให้ตรงกับสถานะล่าสุดก่อนเข้าห้องสอบ)

Q: ใช้เวลาทำโปรเจกต์นี้นานแค่ไหน ส่วนไหนยากที่สุด?
A: (ตอบตามข้อเท็จจริงของตัวเอง) ส่วนที่มักตอบได้อย่างมีน้ำหนักคือ: การ
   ออกแบบ ensemble weighting ให้ยุติธรรมและไม่ leak ข้อมูล test, การหา
   จุดสมดุล hyperparameter ที่ไม่ overfit เกินไป (ต้องทดลองหลายชุดจริง
   ไม่ใช่เดาค่าเดียวแล้วจบ), และการจัดการ concurrency ของการจองห้องไม่ให้
   ซ้อนกัน


================================================================================
บทที่ 10: ข้อจำกัดของงานวิจัย (Limitations) — พูดเองก่อนกรรมการถาม
================================================================================
การพูดถึงข้อจำกัดของงานเองอย่างมั่นใจ (แทนที่จะรอให้กรรมการจับได้) เป็นกล
ยุทธ์การสอบป้องกันที่ได้ผลดีมาก เพราะแสดงว่าเข้าใจงานตัวเองลึกจริง ไม่ใช่
แค่ทำให้เสร็จ ข้อจำกัดที่ควรพูดถึงเองอย่างตรงไปตรงมา:

  1) ขนาดข้อมูลยังเล็ก (ไม่กี่ร้อยแถวต่อห้อง) — เป็นข้อจำกัดหลักที่ส่งผล
     ต่อทุกอย่าง (ทำไม LSTM ไม่ชนะ, ทำไมไม่ใช้ Transformer) ยิ่งสะสมข้อมูล
     การใช้งานจริงนานขึ้น ผลลัพธ์มีโอกาสดีขึ้นได้อีกในอนาคต

  2) ยังไม่มี K-Fold Cross Validation แบบ time-series (walk-forward) — วัด
     ผลจาก 1 split เดียว ยังไม่เห็นความแปรปรวนของผลลัพธ์ข้าม split ต่างๆ
     อาจมีโอกาสที่ตัวเลขที่รายงานเป็นค่าที่ "โชคดี" กับ split นี้โดยเฉพาะ

  3) ยังไม่ได้เปรียบเทียบกับโมเดล baseline อื่นในวงการอย่างเป็นระบบ (เช่น
     ARIMA/Prophet) — มีแค่การเทียบกับ naive persistence baseline (ซึ่งก็
     เป็นก้าวที่ดี แต่ยังไม่ใช่การเทียบกับวิธี classical/SOTA อื่นที่ตีพิมพ์
     ในงานวิจัยด้าน time series forecasting)

  4) ครอบคลุมแค่ 8 ห้องที่มีข้อมูลเพียงพอ — ห้องอื่นในระบบยังจองได้ปกติแต่
     ไม่มี AI กำกับ ทำให้ประโยชน์ของฟีเจอร์นี้ยังจำกัดอยู่แค่บางส่วนของห้อง
     ทั้งหมด

  5) โมเดลพยากรณ์จาก "ประวัติการจอง" เท่านั้น — ยังไม่ได้ผนวกปัจจัยภายนอก
     ที่อาจส่งผลจริง เช่น ปฏิทินกิจกรรมมหาวิทยาลัย (event พิเศษ), สภาพ
     อากาศ, หรือประกาศปิดเรียนกะทันหัน ซึ่งอาจทำให้พยากรณ์คลาดเคลื่อนในวัน
     ที่มีเหตุการณ์ผิดปกติ

  6) Ensemble weighting คำนวณจาก calibration set ที่มีขนาดค่อนข้างเล็ก
     (~10% ของข้อมูลทั้งหมด ซึ่งตัวข้อมูลทั้งหมดก็มีจำกัดอยู่แล้ว) น้ำหนัก
     ที่ได้จึงอาจมีความไม่แน่นอน (variance) สูงกว่าถ้ามีข้อมูลมากกว่านี้

  7) ยังไม่มีการทดสอบกับผู้ใช้จริงจำนวนมากพร้อมกัน (load testing) เพื่อวัด
     ว่าระบบรองรับ concurrent request ได้กี่คำขอพร้อมกันจริง โดยเฉพาะกลไก
     row-level lock ที่อาจกลายเป็นคอขวด (bottleneck) ถ้ามีคนจองห้องเดียวกัน
     พร้อมกันจำนวนมากในเวลาเดียวกันจริงๆ

บทที่ 11: แนวทางพัฒนาต่อ (Future Work) — คำถามท้ายๆ ที่โดนถามแทบทุกครั้ง
================================================================================
  1) เก็บข้อมูลต่อเนื่องแล้วประเมินซ้ำเป็นระยะ — ดูว่าเมื่อข้อมูลมากขึ้น
     LSTM เริ่มแข่งกับ tree-based model ได้มากขึ้นหรือไม่ (ยืนยัน/ปฏิเสธ
     สมมติฐานเรื่องขนาดข้อมูลในบทที่ 10)

  2) ทำ Time Series Cross Validation (walk-forward validation) แทนการวัด
     ผลจาก split เดียว เพื่อความน่าเชื่อถือทางสถิติที่สูงขึ้น

  3) เปรียบเทียบกับ classical baseline อื่นอย่างเป็นระบบ (ARIMA/SARIMAX,
     Prophet) เพื่อยืนยันว่าแนวทาง ML ที่เลือกใช้ดีกว่าจริงในบริบทนี้ ไม่ใช่
     แค่ดีกว่า naive baseline

  4) ผนวกปัจจัยภายนอก (external features) เช่น ปฏิทินกิจกรรมของมหาวิทยาลัย
     ประกาศปิดเรียน เข้าไปเป็น feature เพิ่มเติม

  5) ขยายให้ครอบคลุมห้องทั้งหมดในระบบ ไม่ใช่แค่ 8 ห้องที่มีข้อมูลพอในตอนนี้
     — อาจใช้ transfer learning จากห้องที่มีข้อมูลเยอะไปช่วยห้องที่ข้อมูล
     น้อยกว่า (ต่อยอดจากแนวคิด SeasonalMedianModel/cold-start prior ที่มี
     อยู่แล้ว)

  6) ทำ load testing วัด throughput ของระบบจองภายใต้ concurrent request
     จำนวนมาก และพิจารณา caching ชั้นที่เหมาะสมถ้าจำเป็น

  7) ต่อยอดเป็นแอปมือถือ (mobile app) โดยใช้ REST API เดิมที่มีอยู่แล้ว
     (สถาปัตยกรรมปัจจุบันรองรับอยู่แล้วเพราะแยก backend/frontend ชัดเจน)

บทที่ 12: เทคนิคการตอบคำถามในห้องสอบป้องกัน
================================================================================
  1) ตอบตรงประเด็นก่อนเสมอ (คำตอบสั้นๆ 1-2 ประโยคที่ตรงคำถามที่สุดก่อน)
     แล้วค่อยขยายความ/ยกตัวอย่าง — อย่าเริ่มด้วยการเล่าพื้นหลังยาวๆ ก่อนถึง

  3) ถ้าโดนถามจุดที่เป็นข้อจำกัดจริงของงาน (ดูบทที่ 10) อย่าพยายามกลบเกลื่อน
     ว่า "ไม่มีปัญหา" — ยอมรับตรงๆ ว่าเป็นข้อจำกัด พร้อมอธิบายว่าทำไมถึง
     ยังไม่ได้ทำ (เวลา/ทรัพยากร/ขอบเขตงาน) และมีแผนจะแก้ยังไง (โยงไปบทที่
     11) กรรมการมักให้คะแนนดีกว่าเมื่อเห็นว่าเข้าใจข้อจำกัดของตัวเองจริง
     มากกว่าพยายามอวดว่างานสมบูรณ์แบบ

  4) ถ้าถูกถามคำถามที่ไม่เคยคิดมาก่อนจริงๆ ให้ตั้งสติคิดจากหลักการที่เข้าใจ
     จริง (เช่น หลักการ ensemble, หลักการป้องกัน data leakage) แทนการเดา
     มั่วหรือนิ่งเงียบ — พูดกระบวนการคิดออกมาดังๆ ("ถ้าคิดจากหลักการ X
     น่าจะเป็นแบบนี้เพราะ...") กรรมการมักให้คะแนนกระบวนการคิดที่มีเหตุผล
     แม้คำตอบสุดท้ายจะไม่ตรงเป๊ะ

  5) เตรียมสไลด์/หน้าจอสำรองไว้เปิดโชว์โค้ดจริงได้ทันที ถ้ากรรมการอยากเห็น
     ของจริง (เช่น เปิด forecast.py ไปที่บรรทัดสถาปัตยกรรม LSTM, เปิด
     models.py ไปที่ตาราง Booking) — เตรียม bookmark ไว้ล่วงหน้า ประหยัด
     เวลาหาไฟล์กลางห้องสอบ

  6) ซ้อมพูดสรุปภาพรวมทั้งระบบใน 2-3 นาทีให้คล่องปากก่อนวันสอบ (มักถูกขอ
     ให้ "เล่าภาพรวมโปรเจกต์" เป็นคำถามแรกเสมอ) ใช้โครงจากบทที่ 1-2 ของ
     เอกสารนี้เป็นสคริปต์ตั้งต้น


================================================================================
ภาคผนวก ก: อภิธานศัพท์ (เผื่อถูกขอให้อธิบายคำศัพท์สดในห้องสอบ)
================================================================================
  - Overfitting: โมเดล "จำ" ข้อมูล train ได้ดีมากจนแม่นสูงบน train แต่
    ทำนายข้อมูลใหม่ (test) ได้แย่กว่าที่ควร เพราะเรียนรู้ noise/รายละเอียด
    เฉพาะของ train แทนที่จะเรียนรู้ pattern ทั่วไปที่ใช้ได้กับข้อมูลใหม่

  - R² (R-squared): สัดส่วนความแปรปรวนของข้อมูลจริงที่โมเดลอธิบายได้ ค่า 1
    คือทำนายสมบูรณ์แบบ ค่า 0 คือแย่พอๆ กับการทายค่าเฉลี่ยทุกครั้ง ค่าติดลบ
    คือแย่กว่าการทายค่าเฉลี่ยเฉยๆ เสียอีก

  - MAE (Mean Absolute Error): ค่าเฉลี่ยของ |ค่าจริง - ค่าทำนาย| หน่วยเดียว
    กับข้อมูลจริง (ในงานนี้คือ "ชั่วโมง") ตีความง่ายกว่า MSE เพราะไม่ได้ยก
    กำลังสอง

  - Ensemble: การรวมผลจากหลายโมเดลเข้าด้วยกัน (เช่น ถ่วงน้ำหนักเฉลี่ย หรือ
    เลือกตัวที่ดีที่สุด) เพื่อให้ผลลัพธ์โดยรวมแม่น/เสถียรกว่าใช้โมเดลเดียว

  - Gradient Boosting: วิธีสร้างโมเดลแบบ ensemble ของต้นไม้ตัดสินใจ
    (decision tree) หลายต้น โดยแต่ละต้นใหม่ถูกเทรนมาแก้ไข error ที่ต้น
    ก่อนหน้ายังทำนายผิดอยู่ (เรียนรู้ต่อเนื่องแบบเป็นลำดับ) LightGBM และ
    XGBoost เป็น implementation ของแนวคิดนี้

  - LSTM (Long Short-Term Memory): โครงข่ายประสาทเทียมชนิดหนึ่งที่ออกแบบ
    มาจำ pattern ในข้อมูลลำดับ (sequence/time series) ได้ดีกว่า neural
    network ธรรมดา เพราะมีกลไกจำ/ลืมข้อมูลระยะยาวได้ (gate mechanism)

  - Data Leakage: การที่ข้อมูลซึ่งไม่ควรรู้ล่วงหน้า (เช่นข้อมูลอนาคต หรือ
    ข้อมูล test) หลุดเข้าไปมีอิทธิพลต่อการเทรน/ตัดสินใจของโมเดลโดยไม่ได้
    ตั้งใจ ทำให้ผลวัดที่ได้ดูดีเกินความเป็นจริง

  - Time Series: ข้อมูลที่เรียงลำดับตามเวลา ซึ่งมีคุณสมบัติพิเศษคือค่าที่
    ใกล้เวลากันมักมีความสัมพันธ์กัน (autocorrelation) ทำให้ต้องระวังเรื่อง
    การแบ่งข้อมูล/การตรวจสอบผลต่างจากข้อมูลทั่วไป

  - Race Condition: สถานการณ์ที่ผลลัพธ์ของระบบขึ้นอยู่กับ "จังหวะเวลา" ที่
    หลาย process/request ทำงานแทรกกัน โดยไม่ได้ตั้งใจ ทำให้เกิดผลลัพธ์ที่
    ไม่ถูกต้อง (เช่น การจองซ้อนกัน) ถ้าไม่มีกลไกป้องกัน (เช่น lock)

  - JWT (JSON Web Token): รูปแบบ token ที่เข้ารหัสข้อมูลผู้ใช้/สิทธิ์ไว้ใน
    ตัวเอง ใช้ยืนยันตัวตนโดยที่ server ไม่ต้องเก็บ session state ไว้เอง
    (stateless authentication)

ค.1 สถาปัตยกรรม LSTM (ml/saved/forecast.py)
--------------------------------------------------------------------------------
    model = Sequential([
        LSTM(48, return_sequences=False, input_shape=(lookback, input_cols)),
        Dropout(0.2),
        Dense(16, activation='relu'),
        Dense(1),
    ])
    optimizer = Adam(learning_rate=0.0005, clipvalue=1.0)
    model.compile(optimizer=optimizer, loss='mae', metrics=['mae'])

  อธิบายทีละส่วน:
  - `LSTM(48, return_sequences=False, input_shape=(lookback, input_cols))`
    รับ input เป็น 3 มิติ (batch, lookback, input_cols) คือ "ย้อนหลัง
    กี่วัน" คูณ "กี่ feature ต่อวัน" — return_sequences=False แปลว่าเอา
    output แค่ timestep สุดท้าย (สรุปทั้ง sequence เป็นเวกเตอร์เดียว)
    ไม่ต้องส่ง sequence ต่อไปให้ LSTM ชั้นถัดไป (เพราะมีแค่ชั้นเดียว)
  - `Dropout(0.2)` สุ่มปิด neuron 20% ระหว่างเทรนแต่ละรอบ (ไม่ใช่ตอน
    inference จริง) เป็นเทคนิคป้องกัน overfitting มาตรฐาน
  - `Dense(16, activation='relu')` แปลงเวกเตอร์จาก LSTM (48 มิติ) ให้เหลือ
    16 มิติ ผ่าน non-linear activation (ReLU) ก่อนสรุปเป็นค่าเดียว
  - `Dense(1)` ชั้นสุดท้าย ไม่มี activation (linear) เพราะเป็นงาน
    regression (ทำนายตัวเลขต่อเนื่อง ไม่ใช่ classification ที่ต้องการ
    sigmoid/softmax)
  - `Adam(learning_rate=0.0005, clipvalue=1.0)` — Adam คือ optimizer ที่
    ปรับ learning rate ให้แต่ละ parameter อัตโนมัติ (adaptive) เร็วและ
    เสถียรกว่า plain SGD ในงานส่วนใหญ่ `clipvalue=1.0` จำกัดขนาด gradient
    สูงสุดไม่ให้เกิน 1.0 (gradient clipping) ป้องกัน "exploding gradient"
    ที่ทำให้การเทรนระเบิด/ไม่ลู่เข้า (unstable) ซึ่งเสี่ยงเกิดได้ง่ายกว่า
    ปกติบนข้อมูลจำนวนน้อย
  - `loss='mae'` ใช้ Mean Absolute Error แทน Mean Squared Error (ดูเหตุผล
    ในหัวข้อ 9.1)

ค.2 การป้องกันการจองซ้อน (booking/views.py, BookingViewSet.perform_create)
--------------------------------------------------------------------------------
    def perform_create(self, serializer):
        room       = serializer.validated_data['room']
        start_time = serializer.validated_data['start_time']
        end_time   = serializer.validated_data['end_time']

        with transaction.atomic():
            Room.objects.select_for_update().get(pk=room.pk)

            if Booking.objects.filter(
                room=room,
                status__in=['pending', 'approved', 'checked_in'],
                start_time__lt=end_time,
                end_time__gt=start_time,
            ).exists():
                raise ValidationError({'detail': 'ห้องนี้ถูกจองในช่วงเวลาดังกล่าวแล้ว...'})
            # (ตามด้วยเช็ค TermBooking และ MaintenanceBlock ทับซ้อนแบบเดียวกัน)
            booking = serializer.save(user=self.request.user, status='approved')

  อธิบายทีละส่วน:
  - `transaction.atomic()` เปิด database transaction — ทุกคำสั่งข้างในนับ
    เป็นหน่วยเดียว (all-or-nothing) ถ้ามี exception เกิดขึ้นระหว่างทาง
    (เช่น ValidationError จาก conflict) การเปลี่ยนแปลงทั้งหมดใน block นี้
    จะถูก rollback ทั้งหมด ไม่มีสถานะครึ่งๆ กลางๆ ค้างอยู่ในฐานข้อมูล
  - `Room.objects.select_for_update().get(pk=room.pk)` คือหัวใจของการกัน
    race condition — คำสั่งนี้สั่งฐานข้อมูลให้ "ล็อกแถวนี้ไว้" (SELECT ...
    FOR UPDATE ในภาษา SQL) จนกว่า transaction นี้จะ commit หรือ rollback
    ถ้ามีอีก request หนึ่งพยายาม select_for_update() แถวเดียวกันพร้อมกัน
    request ที่สองจะ "ต้องรอ" จนกว่า request แรกจะจบ transaction ก่อน —
    การ query เช็ค conflict (Booking.objects.filter(...).exists()) ที่ตาม
    มาจึงการันตีว่าเห็นข้อมูลล่าสุดจริงเสมอ ไม่ใช่ข้อมูลที่อาจจะเก่าเพราะ
    อีก request หนึ่งกำลังจะ commit การจองใหม่พร้อมกันอยู่
  - ลำดับสำคัญมาก: ต้องล็อก (select_for_update) ก่อนเช็ค conflict เสมอ
    ถ้าสลับลำดับ (เช็ค conflict ก่อนแล้วค่อยล็อก) จะไม่มีผลป้องกันอะไรเลย
    เพราะช่วงเวลาระหว่างเช็คกับล็อกยังเป็นช่องให้ request อื่นแทรกได้อยู่ดี

ค.3 การยืนยันตัวตน WebSocket ด้วย JWT ผ่าน Query String (room_booking/asgi.py)
--------------------------------------------------------------------------------
  ปัญหา: WebSocket connection จาก browser (JavaScript `new WebSocket(url)`)
  ไม่สามารถแนบ custom HTTP header (เช่น `Authorization: Bearer <token>`)
  แบบที่ทำกับ axios/fetch ปกติได้ตรงๆ (ข้อจำกัดของ WebSocket API มาตรฐาน)
  จึงต้องหาวิธีอื่นส่ง JWT ไปให้ backend รู้ว่าใครกำลังเชื่อมต่ออยู่

  วิธีแก้ในระบบนี้: ส่ง JWT ผ่าน query string ของ URL เอง
      new WebSocket(`${WS_BASE_URL}notifications/?token=${accessToken}`)

  แล้วฝั่ง backend มี Middleware คั่นกลางดักอ่านค่านี้ก่อนส่งต่อให้ Consumer:

    class JWTAuthMiddleware(BaseMiddleware):
        async def __call__(self, scope, receive, send):
            query_string = scope.get('query_string', b'').decode()
            params       = parse_qs(query_string)
            token_list   = params.get('token', [])
            if token_list:
                user = await self.get_user_from_token(token_list[0])
                scope['user'] = user
            else:
                scope['user'] = AnonymousUser()
            return await super().__call__(scope, receive, send)

  อธิบาย: Middleware นี้ถูกครอบ URLRouter ของ WebSocket ไว้ทั้งหมด (ดูใน
  asgi.py: `'websocket': JWTAuthMiddleware(URLRouter(websocket_urlpatterns))`)
  ทำงานเหมือน middleware ฝั่ง HTTP ปกติ คือดักทุก connection ก่อนถึง
  consumer จริง ถอดรหัส JWT (`AccessToken(token)`) ดึง user_id ออกมา แล้ว
  set `scope['user']` ให้ — Consumer (เช่น NotificationConsumer.connect())
  จึงเรียก `self.scope.get('user')` แล้วรู้ทันทีว่าเป็น user คนไหน ใช้สร้าง
  WebSocket group เฉพาะคน (`user_{id}_notifications`) ได้ถูกต้อง

ค.4 กลไก Push แจ้งเตือนอัตโนมัติผ่าน Django Signal (booking/signals.py)
--------------------------------------------------------------------------------
    @receiver(post_save, sender=Notification)
    def push_notification(sender, instance, created, **kwargs):
        if not created:
            return
        channel_layer = get_channel_layer()
        if channel_layer is None:
            return
        async_to_sync(channel_layer.group_send)(
            f'user_{instance.user.id}_notifications',
            {
                'type':       'notification_push',
                'title':      instance.title,
                'message':    instance.message,
                'notif_type': instance.type,
                'booking_id': instance.booking.id if instance.booking else None,
            }
        )

  อธิบาย: `@receiver(post_save, sender=Notification)` คือ Django signal —
  ฟังก์ชันนี้จะถูกเรียกอัตโนมัติทุกครั้งที่มีการ `.save()` ออบเจกต์
  Notification ไม่ว่าจะมาจากที่ไหนในโค้ด (จุดที่สร้าง Notification เช่นตอน
  อนุมัติการจอง ไม่ต้องเรียกฟังก์ชันส่ง WebSocket เองเลย — แค่สร้าง
  Notification.objects.create(...) กลไกนี้ก็ทำงานให้อัตโนมัติ) ทำให้โค้ด
  ส่วน business logic (เช่น perform_create ใน ค.2) ไม่ต้องรู้จัก/ผูกติดกับ
  รายละเอียดของ WebSocket เลย (separation of concerns) — `if not created:
  return` กันไม่ให้ signal นี้ทำงานซ้ำตอน Notification ถูก UPDATE (เช่น
  ตอนกดอ่านแล้ว is_read=True ก็เป็นการ save() เหมือนกัน แต่ไม่ควร push ซ้ำ)
  `async_to_sync(...)` จำเป็นเพราะ Django signal ทำงานแบบ synchronous
  (เหมือนโค้ด Django ทั่วไป) แต่ channel_layer.group_send เป็นฟังก์ชันแบบ
  async (asyncio) จึงต้องมีตัวแปลงเชื่อมสองโลกนี้เข้าด้วยกัน
